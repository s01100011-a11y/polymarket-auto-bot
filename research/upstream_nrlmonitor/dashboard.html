          Model Evaluation Help
          
        

        
Evaluation method

        
Rolling Origin: Train on all games before day D, predict day D, advance daily. No future leakage. Preferred method.

        Chronological Holdout: Fallback when insufficient history. First 80% train, last 20% test.

        
Metrics

        
Brier Score: Mean squared error of predicted probability. Range [0,1], lower = better. Measures overall probability accuracy.

        Log Loss: Cross-entropy loss. Harshly penalises confident wrong predictions. Lower = better.

        ECE (Expected Calibration Error): "When the model says 70%, does it really happen ~70% of the time?" Bins predictions into 10 buckets and compares. Lower = better calibration.

        
Freq vs Bayes

        
Frequency: Simple empirical rate (wins/total per condition).

        Bayesian: Beta posterior with NRL-calibrated priors. Smooths small samples toward expected base rates.

        If Bayes Brier < Freq Brier (shown in green), Bayesian smoothing is helping.

        
Targets

        
Team Wins: Did the condition-firing team win?

        Game Upset: Did the underdog win? (computed from pregame odds — games without odds data are excluded)

        Game Close: Was it a close game (CLOSE tag)?

        Game Blowout: Was it a blowout (BLOWOUT tag)?

        Game Comeback: Was there a comeback (COMEBACK tag)?

      

    

    
    

      

        

          Condition Outcomes Help
          
        

        
Columns

        
Games: Number of times this condition fired (unique per game+team).

        Win%: Percentage of times the team that triggered the condition won.

        Close/Blowout/Comeback: Percentage of games with that postgame tag.

        +/- Margin: Percentage of fires where team had positive/negative margin at fire time.

        Avg Margin: Average score margin at condition fire time (positive = leading).

        Covered%: Percentage of times the triggering team covered the pregame spread.

        
Combinations

        
Shows conditions that co-fired for the same team in the same game. Higher combo sizes (3-5) find synergistic patterns but need more data to be statistically significant.

        
Drill-down

        
Click any condition row to navigate to Game History filtered by that condition.

      

    

    
    

      

        

          PW Accuracy Help
          
        

        
Summary metrics

        
Accuracy: Correct calls / total calls. Flat ROI: +1 unit per correct call, -1 per incorrect. ML ROI: Profit at pregame decimal odds. Spread ROI: +1/-1 units based on pregame spread coverage.

        
Breakdowns

        
By Confidence Band: How accuracy varies by PW confidence level (50-59%, 60-69%, etc.).

        By Consensus: How accuracy differs when ML and historical models agree (Strong) vs disagree (Conflicted).

          PW Performance Trends — Help
          
        

        
Tracks PW call quality metrics over time, linked to specific logic improvements. A new snapshot is automatically captured with each daily backup.


        
Trend Chart

        
Left axis: Accuracy % (blue) and ROI % (green). Right axis: PW call count (gray) and game count (yellow). Vertical dashed yellow lines mark PW logic changes from the changelog.


        
Timeframe Controls (Row 2)

        
    
          
  • Source — Live / Backfill / Other / All. Filters games by how they were recorded.
    • 
          
  • Timeframe — Days (1-120), Months (1-12), Years (1-5), Games (10-500). Selecting a timeframe clears date pickers and vice versa.
    • 
          
  • Date From / To — Custom date range pickers.
    • 
          
  • Interval — How data points are grouped:
    
            Daily — one point per game date. Weekly — per ISO week (e.g. "2026-W21"). Monthly — per calendar month (e.g. "2026-05").
    
            1/5/15/30/60 min — groups by game minute, showing accuracy/ROI by when during the game the call was made.
    • 
          
  • Cumulative / Per Interval — toggle button. Cumulative: each point includes all games up to that date. Per Interval: each point shows only that period's games.
    • 
          
  • Clear — resets all timeframe controls.
    • 
        

        
How it works: Any filter triggers server-side per-game-date computation. No filters active returns stored backup snapshots. Info label shows "N data points, M games, K calls".


        
Filters (Row 1)

        
    
          
  • Role — Favorite / Underdog / All.
    • 
          
  • Half — H1 / H2 / ET / All.
    • 
          
  • Quarter — Q1 (0-20') / Q2 (20-40') / Q3 (40-60') / Q4 (60-80') / ET (80'+) / All.
    • 
          
  • Calls — First / Last / 1st/Half / 1st/Qtr / All.
    • 
          
  • Margin — Trailing / Leading / All.
    • 
          
  • Season — filter by season year. Segment — Regular / Finals / All.
    • 
        


        
Chart Types

        
Performance: Accuracy + ROI trend lines. Unit P&L: Profit/loss in flat units. Rolling: 5-snapshot rolling accuracy vs cumulative. Bankroll: $10k starting capital simulation at $100/bet.


        
ROI Metrics

        
    
          
  • Flat ROI — +1 unit per correct call, -1 per incorrect.
    • 
          
  • ML ROI — profit at pregame decimal odds.
    • 
          
  • Live Spread ROI — synthetic spread cover (pregame spread minus margin at fire).
    • 
          
  • BK Spread ROI — bookmaker's actual live spread and spread price at fire time. Uses actual spread price (juice) when available, falls back to -110 for historical calls without price data. More realistic than synthetic live line.
    • 
          
  • BK ML ROI — return using the bookmaker's h2h moneyline (decimal odds) captured at PW fire time. Unlike ML ROI (pregame odds), this reflects the actual in-game bookmaker moneyline when the prediction was made.
    • 
        


        
Changelog & Version Cohorts

        
Changelog tracks PW algorithm changes with metrics at each date. Version cohort table groups calls by algorithm version active when each call was made.

ROI Matrix — How It Works

          
        

        

          
Cross-dimensional pivot of Predicted Winner call accuracy and ROI. Shows how different combinations of call characteristics perform together.


          
Dimensions

          
    
            
  • Confidence Band — the predicted win probability (50-59%, 60-69%, ..., 90%+)
    • 
            
  • Consensus Type — agreement between prediction signals (strong, conflicted, historical only, ML only)
    • 
            
  • Half — when the prediction was made (H1, H2, or ET)
    • 
            
  • Spread Role — whether the predicted team was the pregame favourite or underdog
    • 
          


          
How to read the matrix

          
Select any two dimensions for the row and column axes. Each cell shows:

          
    
            
  • Games Won % — percentage of unique games where the predicted team won
    • 
            
  • Flat ROI (F) — return on investment assuming $100 flat bets at +1/-1 units
    • 
            
  • ML ROI (ML) — return on investment using actual pregame decimal odds
    • 
            
  • Pregame Spread ROI (Spr) — return on investment from pregame spread bets at -110 juice
    • 
            
  • BK Spread ROI (BkS) — return on investment from the bookmaker's live spread at fire time, using actual spread price (juice) when available, falling back to -110 for historical calls without price data
    • 
            
  • BK ML ROI (BkML) — return on investment using the bookmaker's moneyline (h2h) decimal odds captured at PW fire time
    • 
            
  • Nc/Ng — number of calls / number of unique games in that cell
    • 
          

          
Cell background colour indicates Flat ROI: green tint = positive, red tint = negative. Cells with "---" have insufficient data.


          
Pin controls (4-way cross-tabs)

          
The two dimensions not selected as row/column appear as pin filters. Setting a pin value (e.g., Spread Role = Underdog) filters all cells to only include calls matching that value. This gives you a 3-way or 4-way cross-tab viewed through a readable 2D grid.


          
Season and segment filters

          
The matrix has its own Season and Segment dropdowns, independent of the Analysis tab. Use these to compare ROI across different time periods without affecting other views.


          
Drill-down

          
Tap any cell to navigate to the Game History tab filtered to the matching calls. The Return button brings you back to the ROI Matrix tab. All active pin and season/segment filters are carried through to the drill-down.


          
Tips

          
    
            
  • Look for cells with high Games Won % AND positive ROI — these are the most reliable prediction profiles.
    • 
            
  • High accuracy on favourites often produces low ROI (small payouts). High accuracy on underdogs produces outsized ROI.
    • 
            
  • Small sample cells (low Nc/Ng) should be treated with caution — the results may not be statistically significant.
    • 
            
  • These are backtested results from historical data, not live betting outcomes.
    •

            📊 Odds Monitor History — Stats Explained
            
          


          
Aggregate Stats Card

          
    
            
  • Games — total monitored games in the filtered set.
    • 
            
  • Avg Tries in Window — average tries scored during the monitoring window (minute 70+).
    • 
            
  • Over / Under / Push — how many games' final total was above / below / equal to the total line at the first monitoring snapshot. The total line is the live in-play line when monitoring started (~minute 70), not the pregame line.
    • 
            
  • Under +EV >25% Strategy — simulated results of betting Under on the first snapshot where the EV edge for under exceeds 25%. Shows wins/bets, P&L in units, ROI%.
    • 
          


          
Per-Game Summary Row (collapsed)

          
Date, teams, final score, final total, OVER/UNDER/PUSH result, total line + move (first → last snapshot), snapshot count.


          
Per-Game Expanded Detail

          
    
            
  • Monitoring window — first to last snapshot timestamps.
    • 
            
  • ML + move — home/away moneyline at first snapshot and change to last.
    • 
            
  • Spread + move — home spread at first snapshot and change to last.
    • 
            
  • Spread Covered — whether the home team covered the first snapshot's spread.
    • 
            
  • Tries in window — tries scored during the monitoring window (minute 70+).
    • 
            
  • Best EV Edge — highest EV edge (under) seen across all snapshots for this game.
    • 
            
  • Bookmakers — which bookmakers actually provided odds data for this game (from ML, spread, and totals sources of the first snapshot). May differ per market if the primary bookmaker lacked a market.
    • 
          


          
Bookmaker Priority Order

          
The system selects odds from bookmakers in this priority order. The first available bookmaker with spread data is used as primary; ML and totals fall back independently if the primary lacks those markets.

          
    
            
  1. TAB
  2. PointsBet AU
  3. Ladbrokes AU
    4. 
            
  4. Unibet
  5. Neds
  6. TABtouch
  7. BetRight
    8. 
            
  8. Betr AU
  9. PlayUp
  10. Betfair Exchange AU
    11. 
          


          
How Bookmaker Selection Works

          
Each market is selected independently in a single pass — no retries. The Odds API returns all available bookmakers for a game in one response.

          
    
            
  • ML — first bookmaker in priority order with h2h outcomes → shown as ml_source
    • 
            
  • Spread — first with spreads outcomes → spread_source
    • 
            
  • Totals — first with totals outcomes → totals_source
    • 
          

          
If the primary bookmaker (e.g. TAB) lacks a market, it falls through to the next in the list. A fallback log entry is recorded.

          
Retrying the same API call would return the same data — market availability only changes over time (bookmakers add/pull markets during a game), which is why different snapshots can show different bookmakers for the same market.

    • 
            
  • Total — combined total points at snapshot.
    • 
            
  • Total Line — bookmaker's over/under line at snapshot (with bookmaker name).
    • 
            
  • Over $ / Under $ — decimal odds for over/under bets.
    •

    • 
            
  • Home ML / Away ML — moneyline odds.
    • 
            
  • Tries — cumulative tries in the monitoring window.
    •

            📊 Spread Analysis — Help
            
          


          
The Spread Analysis evaluates the spread strategy's historical performance across multiple dimensions and thresholds, identifying profitable and unprofitable patterns. Both leading and trailing team strategies are computed for every game — use the Context filter to focus on one perspective.


          
Notable Patterns

          
    
            
  • Profitable patterns (green card) — multi-dimension combinations (2D-5D) from 7 core dimensions with ROI > Min ROI and ≥ Min Games. Labelled with dimension level and threshold: [3D @$2.0].
    • 
            
  • Anti-patterns (red card) — combinations with ROI < -(Min ROI) and ≥ Min Games. These are conditions to avoid.
    • 
            
  • Patterns are detected from all combinations of the 7 core dimensions at the configured dimension range (e.g., 2D-3D = 56 combos, 2D-5D = 112 combos). The 7 dimensions: side, role, margin, entry minute, margin context, spread price, EV edge.
    • 
            
  • Click a pattern to set the history table filters to those dimensions and scroll to matching games.
    • 
            
  • ⚠️ Low confidence — shown when a bucket has fewer than 5 games. Results are statistically unreliable and may change significantly with more data.
    • 
          


          
How to read a pattern

          
[3D @$2.0] home + 7-12 + leading: 5/7 covered, ROI +45.2%

          
    
            
  • [3D @$2.0] = 3-dimension combo, computed at threshold $2.00
    • 
            
  • home + 7-12 + leading = home team, leading by 7–12, and was the leading team at entry
    • 
            
  • 5/7 covered = this situation occurred 7 times, spread covered 5 times
    • 
            
  • ROI +45.2% = betting $1 each time would have returned $0.45 profit per dollar staked on average
    • 
            
  • ⚠️ = low confidence — fewer than 5 games, could easily be luck
    • 
          


          
Common dimension values

          

            
ValueDimensionMeaning

            
              
away / homeSideWhether the backed team is the away or home side

              
favorite / underdogRolePregame favorite or underdog (from moneyline odds)

Negative EV edge patterns

          
Some profitable patterns have negative EV edge — the bookmaker's implied probability says the team is unlikely to cover, but historically they do. This suggests the bookmaker may be overcompensating on the spread line for these scenarios, creating value.


          
Using patterns during a live game

          
Example: Rabbitohs (pregame favorite) leading Cowboys by 10 away from home at minute 73:

          
    
            
  1. Check dimensions: away ✅, favorite ✅, margin 7-12 ✅, entry 71-75 ✅
    2. 
            
  2. Look up matching patterns: away+favorite (+95%), favorite+7-12 (+143.8%), 7-12+71-75 (+225%)
    3. 
            
  3. Multiple profitable patterns overlap → stronger signal
    4. 
            
  4. Check the spread price is above your threshold
    5. 
            
  5. Also check no anti-patterns match — if a game matches both profitable and anti-patterns, consider avoiding
    6. 
          

          
Pattern overlap: Multiple matching profitable patterns for the same game is a stronger signal. The more patterns that align, the higher confidence in the bet.


          
Price Threshold & "Best" Option

          
The Price threshold input controls which entry points qualify (spread price ≥ threshold). By default, both the game history table AND the analysis patterns/combos use this same threshold — ensuring consistent click-through from patterns to matching games.

          
    
            
  • "Best" unchecked (default) — analysis uses your price threshold. Patterns and game history are consistent.
    • 
            
  • "Best" checked — analysis uses the sweep-best threshold (highest ROI with 3+ bets). Useful for exploration, but patterns may not match game history at your threshold.
    • 
          

          
Pattern labels show the threshold used: [3D @$2.0] means patterns were computed at $2.00.


          
Threshold Sweep

          
Tests the strategy at 10 price thresholds from $1.50 to $6.00. For each threshold, all historical games are re-evaluated — only snapshots where the spread price ≥ threshold qualify as entry points. Shows:

          
    
            
  • Triggered — games where at least one snapshot qualified at this threshold.
    • 
            
  • Covered — games where the team's final margin + spread line > 0.
    • 
            
  • P&L — total profit/loss in units. Covered = spread_price - 1 units profit; not covered = -1.0 unit loss.
    • 
            
  • ROI — P&L / number of bets × 100%. The highlighted row is the threshold used for the analysis (your threshold, or sweep-best when "Best" is checked).
    • 
          

          
Lower thresholds trigger more bets but may include lower-quality entries. Higher thresholds are more selective but have fewer samples.


          
Dimensional Breakdowns

          
Each dimension splits the triggered games into buckets and shows cover rate, P&L, and ROI per bucket. Computed at the analysis threshold (your price threshold, or sweep-best when "Best" checked). Dimensions:

          
    
            
  • Side — home vs away. Whether the leading/trailing team is the home or away side.
    • 
            
  • Role — favorite vs underdog. Derived from moneyline odds at the entry snapshot — the team with lower ML odds is the favorite. An underdog leading late is in a position the market didn't expect, often with more generous spread prices.
    • 
            
  • Margin — score margin at the entry snapshot: 0-6 (close), 7-12, 13+ (comfortable lead).
    • 
            
  • Entry Minute — game minute when the strategy first triggered: 65-70, 71-75, 76-80.
    • 
            
  • Total Points — final game total: 0-30 (low scoring), 31-40, 41-50, 51+ (high scoring).
    • 
            
  • EV Edge — expected value edge at entry: negative (<0), neutral (0–5%), positive (>5%). Compares historical try probability vs implied probability from the spread price.
    • 
            
  • Spread Price — bookmaker's decimal spread price at entry: $3-4, $4-5, $5+. Higher prices mean the team is a bigger underdog on the spread.
    • 
            
  • Team — which team the strategy backed.
    • 
            
  • Margin Context — whether the backed team was leading or trailing at the entry snapshot. Both perspectives are computed for every game.
    • 
            
  • Competition — NRL Premiership vs State of Origin.
    • 
          


          
Combo Controls

          
    
            
  • Combo dims: [min] to [max] — configure the dimension range for combo analysis (2-5). Default 2-3. Higher dimensions find more specific patterns but require more data.
    • 
            
  • Min Games — hide patterns/combos with fewer than N games (default 3).
    • 
            
  • Min ROI — hide patterns/combos with less than N% absolute ROI (default 20%).
    • 
          


          
Top Combos

          
Multi-dimension combinations from the 7 core dimensions at the configured dimension range, sorted by absolute ROI. Shows the top 30. Each row shows the dimension count (2D/3D/4D/5D), the combo values, games, covered, P&L, and ROI.

          
The 7 core dimensions: side, role, margin, entry minute, margin context, spread price, EV edge.


          
5D Combo Table

          
Cross-dimensional table combining 5 key dimensions: side × role × margin × entry minute × margin context. Each row is a unique 5D combination with ≥3 games. Shows Games, Covered, P&L, and ROI.

          
    
            
  • Sortable — click any column header to sort ascending/descending.
    • 
            
  • Low confidence — ⚠️ shown for combinations with fewer than 5 games.
    • 
            
  • With ~41 BK-tracked games, most 5D combinations will have small samples. This table becomes more useful as the odds monitor accumulates more data.
    • 
          


          
How ROI is Calculated

          
All ROI figures use actual bookmaker spread prices (decimal odds from the entry snapshot). Staking is 1 unit per bet:

          
    
            
  • Covered: profit = spread_price - 1 units (e.g. $3.50 → +2.50u)
    • 
            
  • Not covered: loss = -1.0 unit
    • 
            
  • ROI = total P&L / number of bets × 100%
    • 
          


          
Auto-Update

          
The analysis automatically recomputes after each game is persisted by the Odds Monitor. New patterns are logged to the monitor log when detected. Both leading and trailing strategies are always included — use the Context filter in the history table to focus on one perspective.


          
Important Caveats

          
    
            
  • ⚠️ Small sample sizes — with ~41 BK-tracked games, most buckets have <5 entries. Patterns may be noise. Wait for 50+ games before acting on findings.
    • 
            
  • ⚠️ No out-of-sample testing — all results are in-sample. A pattern found in historical data may not persist in future games.
    • 
            
  • ⚠️ Multiple comparisons — testing many dimension combinations (up to 112 at 2-5D) increases the chance of finding spurious +ROI patterns by luck. Higher Min Games and Min ROI thresholds help filter noise.

Recovery & Backups

      
    

    

      
Three-layer backup system protecting game data against corruption, accidental loss, and host failure. Includes local runtime backups, write-ahead logging, cloud sync to Google Drive, and health monitoring.

      
Three layers of protection

      
    
        
  • Layer 1: Write-Ahead Log (WAL) — game_history.wal records every game completion before writing to the main file. Append-only JSONL that survives corruption.
    • 
        
  • Layer 2: Runtime Backups — runtime_backups/ stores daily snapshots of 14+ runtime state files. Automated via nrl-backup.timer at 16:00 UTC. Retention: last 7 snapshots.
    • 
        
  • Layer 3: Cloud Backup — Full workspace sync to Google Drive via rclone. Daily via nrl-cloud-backup.timer at 02:30 UTC. Google Drive keeps 100 versions per file for 30 days.
    • 
      

      
Auto-Recovery: If game_history.json becomes unreadable, the system automatically restores from the latest runtime backup and replays the WAL.

      
Backup table

      
    
        
  • WAL Recovery Data (top row, green) — games recorded since the last backup. Automatically replayed on restore to ensure no data loss.
    • 
        
  • LATEST badge — marks the most recent backup with the most complete game_history.json.
    • 
        
  • Records — number of game records in the backup
    • 
        
  • Size — backup file size
    • 
        
  • Restore — restores game_history.json from this backup with optional WAL replay.
    • 
      

      
WAL status banner

      
When games complete after the last backup:

      
    
        
  • WAL Active — number of games, date range, file size
    • 
        
  • Latest backup + WAL replay recovers all data with no gaps
    • 
        
  • Empty = no games completed since last backup
    • 
      

      
WAL auto-truncated after each scheduled backup.

      
Cloud Backup History

      
The Cloud Backup History table shows the last 10 cloud backup runs:

      
    
        
  • Started — UTC timestamp when the backup began
    • 
        
  • Status — OK (success) or Errors (non-fatal errors)
    • 
        
  • Size — total data synced
    • 
        
  • Duration — wall time from start to completion
    • 
        
  • Errors — count of non-fatal rclone errors (benign — files sync on next run)
    • 
      

      
Run Now triggers a manual cloud backup. Only one can run at a time.


      
Health monitoring

      
Monitor Status → Overview shows cloud backup status:

      
    
        
  • OK — last backup successful
    • 
        
  • Errors — completed with transient failures
    • 
        
  • STALE (blinking) — last backup >36 hours old
    • 
        
  • Age shows hours since last backup
    • 
      


      
Log rotation

      
logs/cloud_backup.log rotates at 5MB, keeps 3 files (.1, .2, .3).


      
Command-line recovery

      
python3 recovery.py list
python3 recovery.py restore 20260519T160000Z-scheduled
python3 recovery.py restore 20260519T160000Z-scheduled --no-wal
python3 recovery.py wal-status
python3 recovery.py wal-truncate --keep 5

# Cloud backup
./cloud_backup.sh
./cloud_backup.sh --dry-run

      
Auto-recovery steps

      
    
        
  1. Corruption detected (JSONDecodeError)
    2. 
        
  2. [CRITICAL] logged to stderr
    3. 
        
  3. Corrupted file preserved as game_history.json.corrupted
    4. 
        
  4. Latest valid backup restored + WAL replayed
    5.

Best Filter Combos

      
    

    

      
Sweeps dimension filters and ROI thresholds pairwise to find the filter combinations that maximise BK profit units. Results update automatically as PW data changes.


      
Tables

      
Each table ranks the top 3 filter combinations that produce the most units for a specific bet type:

      
    
        
  • Top 3 by BK ML Units — best combos for BK moneyline bets
    • 
        
  • Top 3 by BK Spread Units — best combos for BK spread bets (using BK spread price at fire time)
    • 
        
  • Top 3 by Spread (Pregame) — best combos for pregame spread bets (pregame spread line at 1.91)
    • 
      


      
How it works

      
    
        
  1. Each PW call belongs to a scenario defined by 4 dimensions: Role, Margin, Edge Range, and Quarter.
    2. 
        
  2. The sweep tests 6 dimension filters (Role, Margin, Half, Quarter, Edge, Consensus) pairwise — at most 2 dimensions are set per row, the rest are “—” (all). At least one dimension is always set.
    3. 
        
  3. Within each dimension combo, it sweeps ML ROI≥ (8 values), Spr ROI≥ (8 values), Min Calls (4), Min Games (4), and Logic (AND/OR).
    4. 
        
  4. Surviving scenarios are aggregated to compute total BK ML Units, BK Spread Units, and Pregame Spread Units.
    5. 
      


      
Table columns

      

        
LogicOR = scenario passes if ML ROI or Spr ROI meets threshold. AND = both must pass

        
RoleSpread role filter: favorite, underdog, or — (all)

        
MarginScore margin at fire: leading, trailing, or — (all)

        
HalfHalf filter: H1, H2, ET, or — (all)

        
QtrQuarter filter: Q1–Q4, ET, or — (all)

        
EdgeCondition edge range: 10+, 5-10, 0-5, <0, or — (all)

        
ConsConsensus type: strong, conflicted, ml_only, historical_only, or — (all)

        
ML ROI≥Minimum ML ROI% threshold — scenarios below this are excluded

        
Spr ROI≥Minimum Spread ROI% threshold — scenarios below this are excluded

        
Min CallsMinimum total calls required per scenario (filters out low-sample noise)

        
Min GamesMinimum distinct games required per scenario

        
ScenariosNumber of scenarios that pass all thresholds

        
BetsTotal calls with odds data across surviving scenarios

        
UnitsCumulative profit/loss in $100 units

        
ROIReturn on investment: units ÷ bets × 100%. Calculated per table’s ranking metric (ML ROI for ML table, Spread ROI for Spread table, etc.)

      


      
Min Bets / Games filter

      
Use Min Bets and Games inputs next to the Lock checkboxes to filter combo rows by minimum aggregate totals. Unlike the scenario-level Min Calls/Min Games (which filter individual scenarios within a combo), these filter on the combo row’s total bets and distinct games. Useful for excluding combos with too few data points for reliable ROI.


      
Why “—” appears

      
“—” means all values (no filter) for that dimension. Dimensions are swept pairwise — at most 2 are set per row. For example, a row showing favorite + 5-10 edge with — for Margin, Half, and Qtr means: filter to favourites with edge 5-10, all halves, all quarters, all margins.


      
Example

      
OR  |  underdog  |  trailing  |  —  |  Q3  |  —  |  5%  |  0%  |  10  |  2  |  8  |  142  |  +23.5u

      
Reads: “Filter to underdog calls while trailing in Q3, using scenarios where ML ROI ≥ 5% or Spr ROI ≥ 0% (with ≥10 calls and ≥2 games per scenario) → 8 qualifying scenarios, 142 bets, +23.5 units.”


      
Lock dimensions

      
Use the Lock checkboxes next to the header to force specific dimensions to always appear in results. When a dimension is locked, every combo row must have a non-“—” value for that dimension. For example, locking Quarter ensures every row specifies a quarter (Q1–Q4 or ET) instead of “—”.

      
Click All/None to toggle all locks on or off. Lock state is persisted to localStorage and restored on page load. Tables update instantly without re-fetching data. If no combos match the locked dimensions, a “No combos match” message appears.


      
How to use

      
Click Apply to set the dimension filters (Role, Margin, Half, Quarter, Edge, Consensus) and scenario ROI thresholds to match that row. Non-exempt filters (everything except Season, Segment, and Call Selection) are reset before applying. Click Clear combo filters to remove the applied combo. Click Restore previous filters (appears after Apply) to return to your exact filter state from before Apply was clicked.

      
Note: Past performance does not guarantee future results. Combos with very few scenarios or bets may be noise. Prefer combos with higher scenario counts.

      Slack Alert Setup Guide
      
    

    
What is the bot token?

    
The Slack bot token (xoxb-...) authenticates API calls to send alert messages to your Slack workspace. It's used by monitor.py to post condition alerts, PW alerts, and game-end summaries.

    
How to generate a bot token

    
    
      
  1. Go to api.slack.com/apps
    2. 
      
  2. Click "Create New App" → "From scratch"
    3. 
      
  3. Name it (e.g. "NRL Monitor") and select your workspace
    4. 
      
  4. Go to OAuth & Permissions in the sidebar
    5. 
      
  5. Under Bot Token Scopes, add:
    
        chat:write — send messages
    
        chat:write.public — post to channels without joining
    6. 
      
  6. Click "Install to Workspace" at the top
    7. 
      
  7. Copy the Bot User OAuth Token — starts with xoxb-
    8. 
    

    
Finding the Channel ID

    
Right-click the target channel in Slack → "View channel details" → the ID is at the bottom (e.g. C0B4HFXE4PK).

    
Alert Mode

    
Each condition has an alert_mode setting:

      None — no alert at all

      History only — written to alert history, not sent to Slack

      Slack + History — sent to Slack AND written to alert history
