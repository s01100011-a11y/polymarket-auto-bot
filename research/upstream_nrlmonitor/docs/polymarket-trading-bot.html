Build an automated trading pipeline that receives PW (Predicted Winner) signals from the NBA/WNBA monitor and places orders on Polymarket game-winner markets when the signal shows positive edge against the market price.

Core Thesis

PW calls predict the game winner with ~70% accuracy. Polymarket game-winner markets price outcomes as probabilities. When a PW call fires at 75% confidence and the market prices the same outcome at 60%, there is a theoretical 15-point edge. The bot would buy YES tokens at $0.60 for a predicted $0.75 fair value.

Critical caveat: backfill-derived ROI

98% of NBA PW calls (262 of 15,477) have live-priced bookmaker odds. The remaining 98% are backfill-derived with synthetic odds. Historical ROI figures may not reflect achievable live trading returns. WNBA has 37% live-priced calls. A rigorous paper-trading phase is essential before any real capital deployment.

02PW Signal Quality Assessment

Understanding the signal we would be trading on — its accuracy, calibration, latency, and known biases.

Signal Characteristics

  • Multi-fire deduplication: PW fires multiple times per game (every poll cycle where conditions are met). The first fire in a game carries the most edge; subsequent fires on the same team are confirmations with diminishing marginal value. Only the first fire per game should trigger a trade.
  • Consensus types: strong (ML + historical agree), ml_only, historical_only, conflicted. Strong consensus calls have higher accuracy and should receive larger position sizes.
  • Quarter weighting: Q1 calls (0.85x) are discounted vs Q3/Q4 calls (1.0–1.10x). Earlier calls have more time for edge to materialise but lower confidence.
  • Margin gates: PW is suppressed when trailing by >15 (general) or >10 (late game). These gates prevent chasing lost causes.
  • Edge gate: Average condition edge must exceed pw_edge_gate threshold. Calls with higher edge tend to be more reliable.

Known Biases & Limitations

high Backfill contamination in ROI metrics

98% of NBA PW calls use synthetic/backfill odds. Historical ROI computed from these calls reflects model fit to historical data, not live trading edge. Polymarket prices will differ from both BK odds and synthetic odds.

Mitigation: Paper-trade for 50+ games using live Polymarket prices before deploying capital. Only evaluate ROI on the live-priced subset (262 NBA calls) for realistic expectations.

medium PW confidence is not a calibrated probability

PW's blended confidence percentage is a weighted combination of ML prediction, Bayesian posteriors, quarter weights, and margin boosts. It is not calibrated to true outcome probability. A call at 75% confidence does not mean the team wins 75% of the time.

Mitigation: During paper trading, build a calibration curve mapping PW confidence bands to observed win rates. Use the calibrated probability (not raw confidence) for edge calculation against Polymarket prices.

medium Latency: 30s poll cycle + webhook transit

PW signals arrive with ~30s granularity (monitor poll cycle) plus webhook delivery time to the remote bot. Polymarket game-winner markets move slowly (not HFT), but a 30–60 second delay means the market may have already moved on the same information (score change, momentum shift).

Mitigation: Fetch Polymarket price at order time and re-evaluate edge. Reject trades where edge has decayed below threshold since signal generation.

04System Architecture

Two-node architecture: the existing AU-based monitor generates signals; a remote trading bot in an unrestricted jurisdiction executes trades.

AU Server (monitor.py) Remote VPS (trading bot) ┌──────────────────────────────┐ ┌───────────────────────────────────┐ │ PW call fires │ │ 1. Webhook listener (HTTPS) │ │ predicted_team, game_id │───HTTPS POST───▶ │ 2. Market resolver (Gamma API) │ │ confidence_pct, quarter │ (HMAC-signed) │ 3. Price check (CLOB orderbook) │ │ margin, consensus, edge │ │ 4. Edge evaluation (calibrated) │ │ home_team, away_team, date │ │ 5. Order placement (py-clob-client) │ │ │ │ 6. Position tracking + P&L │ │ save_state() ─▶ .alert_state.json │ │ 7. Auto-exit at game end │ └──────────────────────────────┘ └───────────────────────────────────┘ │ ┌───────┴───────────────────┐ │ Polymarket CLOB API │ │ (Polygon / USDC) │ └───────────────────────────┘

Design Principles

  1. Separation of concerns: Monitor generates signals; bot evaluates and executes. Monitor has zero knowledge of trading state or wallet.
  2. Fail-safe defaults: If the bot is unreachable, signals are dropped (no queuing). If edge evaluation fails, no trade is placed. If Polymarket is unreachable, position is held to settlement.
  3. Idempotent signals: Multiple PW fires for the same team in the same game produce duplicate webhooks. Bot must deduplicate by (game_id, predicted_team) and only trade on the first signal.
  4. No shared state: The trading bot is a standalone service. It does not read monitor state files. All context arrives via the webhook payload.
  5. Audit trail: Every signal received, edge evaluation, order placed, fill received, and P&L outcome is logged with full context for post-hoc analysis.

The trading bot is a separate service that receives PW signals, evaluates edge against Polymarket prices, and places orders.

Market Resolution Logic

# Slug construction
def polymarket_slug(league, home_team, away_team, game_date):
    """
    Polymarket slug pattern:
      nba-{away_slug}-{home_slug}-{YYYY-MM-DD}
      wnba-{away_slug}-{home_slug}-{YYYY-MM-DD}

    Team slugs: lowercase, hyphens for spaces,
    drop "the" prefix, handle edge cases (76ers, trail-blazers)
    """
    away_slug = slugify(away_team)
    home_slug = slugify(home_team)
    return f"{league}-{away_slug}-{home_slug}-{game_date}"

# Query Gamma API for token IDs
GET https://gamma-api.polymarket.com/markets?slug={slug}
  -> condition_id, token_ids (YES token for each team)

Order Placement Flow

  1. Receive webhook → validate HMAC → parse signal
  2. Dedup check: skip if (game_id, predicted_team) already traded
  3. Resolve market: slug → Gamma API → token ID for predicted team YES
  4. Fetch orderbook: CLOB API → best ask price for YES token
  5. Edge evaluation: calibrated PW probability vs ask price (see Section 7)
  6. If edge ≥ threshold: compute position size (see Section 8)
  7. Place limit BUY at best ask + slippage allowance (e.g., +$0.01)
  8. Monitor fill status. If unfilled after 60s, cancel and log.
  9. On fill: record position in state file. Begin settlement monitoring.

07Edge Evaluation & Sizing

How to determine whether a PW signal has genuine edge against the Polymarket price, and how much to wager.

Edge Calculation

# Raw PW confidence is NOT a calibrated probability.
# Must map through calibration curve built during paper trading.
calibrated_prob = calibration_curve.transform(pw_confidence_pct / 100)

# Polymarket implied probability = ask price
market_prob = polymarket_ask_price  # e.g., 0.62

# Edge = calibrated probability - market probability
edge = calibrated_prob - market_prob  # e.g., 0.73 - 0.62 = 0.11

# Expected value per $1 risked
ev = calibrated_prob * (1.0 / market_prob - 1) - (1 - calibrated_prob)
   # = 0.73 * (1/0.62 - 1) - 0.27
   # = 0.73 * 0.613 - 0.27
   # = 0.447 - 0.27 = +0.177 (+17.7% EV)

Minimum Edge Thresholds

ParameterRecommendedRationale
min_edge0.08 (8pp)Covers Polymarket taker fee (~2%) + calibration uncertainty + slippage
min_ev0.05 (5%)Minimum expected value to justify the position
max_price0.90Don't buy YES tokens above $0.90 (too little upside for the risk)
min_price0.15Don't buy YES tokens below $0.15 (likely thin liquidity, high variance)

Calibration Curve

During paper trading, collect (PW confidence, actual outcome) pairs. Fit isotonic regression or Platt scaling to produce a monotonic mapping from raw PW confidence to true win probability. Re-calibrate weekly as more data accumulates.

Existing infrastructure

The evaluate_model.py module already computes ECE (Expected Calibration Error) and Brier scores. These can be extended to produce the calibration curve. The PW trend system tracks accuracy by confidence band, providing the raw data for calibration.

Position Sizing

Use fractional Kelly criterion (half-Kelly recommended for conservative sizing):

# Kelly fraction
f_kelly = edge / (1 / market_prob - 1)
         = (calibrated_prob - market_prob) / (1 - market_prob)

# Half-Kelly for safety
f_half_kelly = f_kelly / 2

# Position size
position_usd = bankroll * f_half_kelly

# Apply caps
position_usd = min(position_usd, max_bet_per_game)
position_usd = min(position_usd, max_total_exposure - current_exposure)

Consensus-Based Multipliers

ConsensusMultiplierRationale
strong1.0xML + historical agree. Full Kelly fraction.
blended0.8xWeighted blend. Slightly reduced.
ml_only0.5xOnly ML model predicts. Historical disagrees or insufficient data.
historical_only0.5xOnly Bayesian predicts. ML disagrees.
conflicted0.0xDo not trade. ML and historical actively disagree.

Liquidity Guards

  • Minimum volume: Skip markets with <$5,000 total volume (likely too thin for reliable execution).
  • Maximum spread: Skip if bid-ask spread >$0.05 (5 cents). Wide spreads indicate illiquid markets.
  • Depth check: Ensure sufficient depth at the ask to fill the intended position size without significant slippage.
  • Slippage cap: Maximum acceptable slippage of $0.02 from quoted ask at signal time.

Kill Switch

  • trading_enabled: false in bot config → signals are received, evaluated, and logged, but no orders are placed.
  • Dashboard integration: button to toggle kill switch remotely via Tailscale API.
  • Automatic kill: triggered when daily loss exceeds max_daily_loss or wallet balance falls below min_wallet_balance.

11Paper Trading Phase

Mandatory simulation period before any real capital deployment. Minimum 50 games recommended.

Paper Trading Requirements

  1. Full pipeline execution: Receive real PW signals, resolve real Polymarket markets, fetch real prices, evaluate edge, simulate order placement — everything except the actual CLOB order.
  2. Realistic fill simulation: Assume fill at ask price + 1 cent slippage. Record simulated position.
  3. Settlement tracking: Monitor real game outcomes. Compute P&L as if positions were real.
  4. Calibration curve construction: Build the PW confidence → true probability mapping from paper trade data.
  5. Edge decay measurement: Track how much Polymarket price moves between signal generation (PW fire) and simulated order placement. Quantify typical edge decay.

Success Criteria to Go Live

Market availability≥ 80% of PW games have Polymarket markets

Backtesting Opportunity

Historical PW calls (15,477 NBA, ~3,000 WNBA) can be paired with historical Polymarket price data (if available via Gamma API historical endpoint) to run a larger-scale backtest. However, this has the same backfill contamination risk as BK odds ROI — treat results as directional, not definitive.

12Implementation Phases

Five phases from investigation to live trading, each with clear deliverables and go/no-go gates.

Phase 1: Market Investigation

phase 1 Polymarket market survey & liquidity assessment

Before writing any code, survey NBA and WNBA game-winner markets on Polymarket to validate assumptions about market availability, liquidity, and pricing.

Deliverables:
  • Script to query Gamma API for all NBA/WNBA game-winner markets for a given date range

Phase 2: Signal Relay

phase 2 Webhook emission from monitor.py

Add webhook POST to monitor.py triggered on PW call fire. Includes HMAC signing, configurable filters, and timeout handling.

Deliverables:
  • Config fields: polymarket_webhook_url, polymarket_webhook_secret, polymarket_min_confidence
  • Webhook POST with full PW call context (see Section 5 payload)
  • Fire-and-forget with configurable timeout (default 5s)
  • Dashboard log entry on webhook send/fail
Go/no-go: Webhook delivers reliably to test endpoint with <2s latency.

Phase 3: Trading Bot Core

phase 3 Bot deployment with paper trading

Deploy the trading bot on remote VPS. Receives signals, resolves markets, evaluates edge, simulates trades. No real orders.

Deliverables:
  • Webhook listener with HMAC validation
  • Market resolver (slug → Gamma API → token ID)
  • Price fetcher (CLOB orderbook query)
  • Edge evaluator (initially using raw PW confidence; calibration added iteratively)
  • Paper trade logger (JSONL with full signal + market context + simulated P&L)
  • Systemd service with auto-restart
  • Settlement monitor (poll Gamma for resolution, compute final P&L)
Go/no-go: 50+ paper trades completed. Simulated ROI > 0%. Calibration curve constructed.

Phase 4: Live Trading (Small Stakes)

phase 4 Real orders with minimal capital

Enable real order placement with conservative limits: $10 max per game, $100 max total exposure. Validate execution quality against paper trade assumptions.

Deliverables:
  • Order placement via py-clob-client
  • Position tracking with real fill prices
  • Execution quality report: actual slippage vs simulated, fill rate, latency
  • Kill switch (config toggle + auto-kill on daily loss)
  • All risk management controls active (Section 8)
  • Wallet balance monitoring with alerts
Go/no-go: 20+ live trades. Execution quality within 2 cents of simulation. No unexpected failures.

Phase 5: Scale Up

phase 5 Increase position sizes and add features

Raise limits to production levels based on Phase 4 results. Add Kelly sizing, consensus multipliers, and dashboard integration.

Deliverables:
  • Half-Kelly position sizing with consensus multipliers
  • Raised limits: $50/game, $500 total exposure
  • Dashboard panel: open positions, P&L history, edge distribution, execution quality
  • Weekly calibration curve refresh
  • WNBA market support (if Phase 1 shows adequate liquidity)
  • Monthly performance review process

Key Risks

critical No edge may exist

Polymarket prices may already incorporate the same information that PW uses (score, momentum, public sentiment). If the market is efficient for NBA game winners, PW signals offer no edge over market prices. This is the fundamental risk.

Mitigation: Phase 1 investigation + Phase 3 paper trading will determine whether edge exists before any capital is risked.

high Geo-restriction tightening

Polymarket has been expanding its restricted country list. Singapore or Malaysia could be added, requiring VPS migration. Account could be flagged for unusual trading patterns.

Mitigation: Monitor Polymarket geo-restriction changes. Maintain ability to migrate to alternative jurisdiction (EU/Ireland). Keep position sizes small enough that a sudden account freeze is not catastrophic.

high Smart contract / wallet risk

USDC held in a Polygon wallet is subject to smart contract bugs, wallet compromise, or bridge failures. Unlike a bank account, there is no recourse for lost funds.

Mitigation: Use a dedicated wallet with only trading capital (not savings). Hardware wallet for signing if supported. Keep wallet balance at operating minimum — top up in small increments.

medium PW model drift degrades signal quality

The ML model retrains weekly on a schedule with no drift detection (see ML training investigation). If model quality degrades, the bot continues trading on stale signals until the next retrain.

Mitigation: Weekly calibration curve refresh detects accuracy drift. Auto-kill if rolling 20-trade accuracy drops below 55%.
