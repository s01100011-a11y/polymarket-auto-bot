Engineering & analytics audit · 26 July 2026

NRLMonitor

A review of the codebase, its reliability posture, and the soundness of the prediction and ROI analytics that sit on top of it.

73 files · 23,883 lines of Python server.py 5,129 · monitor.py 2,309 · dashboard.html 10,813 Source: NRLMonitor-master.zip

The engineering is ambitious and the data pipeline is genuinely good. Two-phase backfill, a WAL, atomic writes, snapshot/restore, a recovery scanner, 26 condition evaluators and 21 timeline features across 514 games — that is real infrastructure, and most of it works.

Two silent runtime defects mean documented features have never run. A use-before-assignment in monitor.py breaks auto-recovery on every cycle; an undefined variable in server.py stops snapshot pruning. Both are swallowed by broad except Exception handlers. A one-second pyflakes run finds both.

The dashboard server has no authentication and serves config.json over HTTP. It binds to all interfaces. Your Slack bot token and Odds API key are one GET request away from anyone on the network, and unauthenticated POST endpoints can delete directories.

The betting analytics are the part that needs the most work. The 98.9% model accuracy is target leakage, not skill — the final score margin is a feature and the winner is the label. The combo leaderboard mines hundreds of cells with no correction for multiple testing.

And the price attached to each call is usually the wrong price. ROI is flat 1 unit at call["moneyline"], which is the correct convention — but for every backfilled game that field holds the pregame line, so a signal firing at minute 72 is booked at the odds available before kickoff. The strict_bk filter does not exclude these, because backfill writes the same pregame number into bk_moneyline. No ROI figure currently on the dashboard should be used to size a bet.

Summary

Can the current ROI data be relied on for betting? No — for three independent reasons, each sufficient on its own.

  1. Wrong prices. Backfilled calls are booked at pregame odds for mid-game signals. The bias runs one way and is largest on the strategies that look best.
  2. Selection. The combo grid ranks hundreds of cells by ROI with no holdout, no minimum sample and no interval. Its top entries are chosen for looking good.
  3. The signal isn't reproducible. PW calls blend ml_model.predict_winner() with outcomes win%, and the ML half reads the final scoreline.

Does filtering to strict_bk fix it? No. That filter gates on bk_moneyline being non-empty, and backfill populates it with the pregame line. It excludes calls with no odds, not calls with stale odds. A filter on bk_ml_source or bk_spread_price would work — those are written only by monitor.py from a live quote.

Full detail in Section 05; the forward-testing protocol that replaces backtesting until this is fixed is in Section 06.

Section 01Code defects

Everything below was confirmed against the source. Line numbers refer to the files as shipped in the archive.

SO-01Send-off

Auto-recovery has never worked — now is used before it is assigned

monitor.py:1179, 1191, 1208, 1230 read now. The only assignment in main() is at line 1246. Because now is assigned somewhere in the function, Python treats it as local for the whole function, so every earlier read raises UnboundLocalError.

The write at line 1208 (state[_chk_key] = now.isoformat()) sits inside except Exception, so each scan fails and logs a warning; because the state key is never written, the next cycle repeats the same failure. The per-game recovery call at line 1230 fails the same way. Net effect: the round scan never completes, missed games are never recovered, and the only trace is a WARN line in the log.

Worse, lines 1179 and 1191 are guarded only by except (ValueError, TypeError). UnboundLocalError subclasses NameError, so it escapes. If a recovery_checked_* key ever appears in .alert_state.json — via a restored snapshot, a hand edit, or a future code path — main() will terminate with an uncaught traceback before any alerts are sent, and the end-of-cycle save_state() will never run.

FixHoist now = datetime.now(timezone.utc) to the top of main() and delete the line 1246 assignment. Then add a regression test that runs one cycle against a fixture draw with a populated recovery_checked_* key.
SO-02Send-off

Snapshot pruning is dead code — new_config is undefined

server.py:4817 reads new_config.get("backup_retention", {}). new_config appears exactly once in the entire 5,129-line file. The local variable is called payload.

The resulting NameError is caught by except Exception: pass at line 4820, so prune_old_snapshots() is never reached. Every config save writes a pre-config-save snapshot of the runtime files and nothing ever removes them. On a box that has been running a season, runtime_backups/ will grow without bound — and the disk-space figure in /api/monitor-status is the thing that will notice first.

Fix_bk_ret = payload.get("backup_retention", {}). Then check the size of runtime_backups/ on the live box and prune manually once.
SO-03Send-off

The history cache is shared mutable state, and request handlers mutate it

_load_history_cached() (server.py:410) returns list(records) — a shallow copy. The nested game dicts, and the predicted_winner_calls lists inside them, are the same objects every caller receives.

_enrich_pw_call(c, r, _edge_store) at server.py:2505 mutates those call dicts in place, writing quarter, spread_role, live_line, bk_live_line and condition_edge onto them. The server is ThreadingMixIn, so two concurrent dashboard requests enrich the same objects at the same time, with different filter parameters. Results bleed between requests and the cache accumulates derived fields that were computed under someone else's filters.

FixMake _enrich_pw_call pure — take a call dict, return a new enriched dict. Alternatively copy.deepcopy on cache read, but that will hurt at 514+ games; the pure function is the better shape and is also easier to test.
SB-01Sin bin

Concurrent writers race on shared .tmp paths

The atomic-write pattern (write tmp → os.replace) is correct, but several call sites use a fixed suffix rather than a PID-qualified one: monitor.py:100, 108, 280, 2057, backfill.py:953, backfill_odds.py:278, and the config write at server.py:4824. Others already do it correctly (outcomes.py:716, odds_api.py:219, ml_train_runner.py:77).

Five processes touch game_history.json: the per-minute monitor, the server's background threads, odds_monitor, backfill.py and recovery.py. Two writing at once through the same .tmp path will interleave and one will win with a partially-written file. There is no cross-process lock anywhere in the tree.

FixShort term: PID-qualify every temp path and add an fcntl.flock advisory lock around read-modify-write of game_history.json. Proper fix in Section 03.
SB-02Sin bin

Whole-file rewrite on every completed game

append_game_record() (monitor.py:126) loads the entire history JSON, scans it for duplicate match_id, appends, and rewrites the whole file with indent=2. At 514 games that is tolerable; the cost is O(n) per game and the file is re-serialised in full each time, on a box also running the dashboard.

FixThe WAL already exists and is the right idea — the missing half is a store that supports append. See SQLite recommendation in Section 03.
SB-03Sin bin

evaluate_red_card has a stub fallback that does nothing

conditions.py:668–687. When the sendOffs stat is absent or zero the function enters a PBP fallback, assigns pbp = team_ctx.get("pbp_features", {}) and side = team_ctx.get("team_side", "home"), uses neither, and sets val = val or 0. The comment says "sendOffs might be in timeline events — check if available"; the check was never written.

So red_card only fires if NRL.com happens to publish the stat key, and never from the timeline. It is listed as a working condition type in the README and is a feature in the trained model's input vector.

FixEither implement the timeline scan for send-off events, or remove the dead branch and document the condition as stats-only. Silently half-implemented is the worst of the three.
PE-01Penalty

Duplicate dictionary key in the postgame payload

server.py:1722 and 1733 both set "round_title" in the same dict literal. Harmless today (both read the same source field) but it is a copy-paste artefact in a 90-line literal, and the class of mistake that eventually assigns two different values.

FixDelete the duplicate. A linter in CI catches this for free.

Section 02Security

The dashboard server has no authentication of any kind — no token, no session, no origin check. It binds to every interface. That single decision is what makes the rest of this section serious.

SO-04Send-off

Your Slack token and Odds API key are served over HTTP

/api/config is careful — it strips slack_bot_token and openclaw_token before responding (server.py:3805). The static file handler underneath (server.py:4755–4785) then serves any file in the script directory, and config.json lives in the script directory.

GET http://<host>:8898/config.json
→ {"slack_bot_token": "xoxb-…", "openclaw_token": "…", "odds_api_key": "…", …}

Two secondary points. The masking on /api/config omits odds_api_key, so that one leaks through the API as well. And main() binds ("", PORT) — all interfaces, not loopback — so anything on the LAN can ask.

FixThree things, in order: (1) rotate the Slack token and Odds API key now, on the assumption they are already exposed; (2) allow-list the static handler to dashboard.html and known assets rather than serving whatever is on disk; (3) move secrets out of config.json into environment variables read at startup, so a file-read bug cannot leak them at all.
SO-05Send-off

Unauthenticated directory deletion with a traversable path

POST /api/recovery/delete-backup (server.py:4904) takes names from the request body and does:

backup_dir = os.path.join(runtime_backup.DEFAULT_BACKUP_ROOT, name)
if os.path.isdir(backup_dir):
    shutil.rmtree(backup_dir)

There is no os.path.basename(), no containment check that the resolved path is still under the backup root, and no authentication. A name of ../../something escapes the root and deletes a directory tree as the service user.

/api/recovery/restore and /api/recovery/prune-backups take the same shape of input, /api/config rewrites your configuration, /api/cloud-backup/run spawns bash cloud_backup.sh, and /api/ml-train kicks off a training run. All unauthenticated.

Fixname = os.path.basename(name), then verify os.path.realpath(backup_dir).startswith(os.path.realpath(BACKUP_ROOT) + os.sep) before touching anything. Apply the same guard to restore and prune.
SO-06Send-off

Any website you visit can drive the dashboard

send_json sets Access-Control-Allow-Origin: * on every response and do_OPTIONS allows GET, POST from anywhere. With no session, no CSRF token and no Origin check, a page in a browser tab can issue POSTs to the dashboard's host and port and they will be honoured. Combined with SO-05, a malicious page can delete your backups; combined with SO-04 and a DNS-rebinding technique, it can read your tokens.

FixDrop the wildcard CORS header entirely — the dashboard is same-origin and does not need it. Add a shared-secret header or a session cookie, and validate Origin/Host on every state-changing request. If you want phone access, put it behind Tailscale or a reverse proxy with auth rather than opening the port.
SB-04Sin bin

The model is loaded with pickle

ml_model.load_model() (ml_model.py:222) unpickles model_nrl.pkl. Unpickling executes arbitrary code by design. Anyone who can write that file — including via the restore endpoint in SO-05 — gets code execution inside the monitor process.

FixA logistic regression is a coefficient vector, an intercept, and the scaler's means and scales. Serialise those to JSON and reconstruct at load time; you also get a diffable, reviewable model artefact and lose the scikit-learn version-compatibility trap.
PE-03Penalty

Config save can drop secrets if a field is ever renamed

POST /api/config re-injects slack_bot_token and openclaw_token from the current file when they are absent from the payload (server.py:4804). That works, but it is a hardcoded list that has to be kept in sync with the masking list on GET — and the two lists already disagree about odds_api_key. The next secret added will be silently wiped by the first config save from the dashboard.

FixOne SECRET_KEYS constant used by both the GET mask and the POST merge. Better still, secrets in the environment (see SO-04) and this problem disappears.

Section 03Architecture

The system has outgrown the shape it started in. Three specific structural choices are now costing you.

JSON files as a database

Every analytical endpoint reloads the full history and scans it in Python. build_pw_calls_payload constructs a ConditionEdgeStore over the entire history per request. build_pw_roi_combos_payload enumerates the full role × margin × selection × half × quarter cross-product per request. The filtering, grouping and aggregation you have hand-written across server.py, audit_roi.py, pw_matrix.py and pw_trend.py is, almost line for line, what a database does.

Recommendation: SQLite in WAL mode. It is a single portable file, it needs no server, it gives you real transactions and multi-process concurrency (which fixes SB-01 outright), indices on game_id/season/ts, and it turns the combo enumeration into a GROUP BY. Keep a JSON export command for portability and for the snapshot system. Schema sketch:

games(game_id PK, season, round, kickoff_utc, home, away,
      home_score, away_score, winner, venue, segment)
conditions_fired(game_id FK, ts, game_minute, type, team, side, detail)
pw_calls(game_id FK, ts, game_minute, predicted_team, confidence,
         margin_at_fire, spread_role, correct)
odds(game_id FK, ts, book, market, side, price, line, is_closing)
bets(id PK, game_id FK, ts, market, side, price, line, stake,
     model_prob, market_prob_devig, ev, result, pnl, closing_price)

That bets table is the one that does not exist today and matters most — see Section 05.

Two modules doing everything

server.py is 5,129 lines and 220 KB. It contains HTTP routing, every payload builder, the ROI mathematics, backup orchestration, log rotation, ML training supervision and three background threads. monitor.py is 2,309 lines with the polling loop, condition dispatch, recovery, odds polling, alerting and persistence all in main(). Imports are scattered inside functions (import subprocess, import outcomes, import runtime_backup, import nrl_api as _nrl) — the usual signature of circular-import avoidance.

Suggested split, without rewriting behaviour:

nrlmonitor/
  core/      config, store (sqlite), models, logging
  ingest/    nrl_api, odds_api, backfill, recovery
  analysis/  conditions, timeline_features, outcomes, roi, calibration
  predict/   features, train, evaluate, registry
  web/       app.py (routing only), api/*.py (one module per endpoint group)
  cli/       monitor, backfill, train, audit

Move the ROI mathematics into analysis/roi.py as pure functions with no I/O. That is what makes it testable, and it is currently duplicated between server.py and audit_roi.py — _roi_pct is defined in both, and again locally at audit_roi.py:788.

The HTTP layer

BaseHTTPRequestHandler + ThreadingMixIn gives you thread-per-connection with no request timeouts, no body size limits, no backpressure and no middleware hook — which is why there is nowhere natural to put authentication. Moving to FastAPI or Flask behind uvicorn/gunicorn gets you auth middleware, request validation from your existing config schema, automatic API docs, and connection limits, without touching the payload builders.

Generated artefacts are in version control

pw_roi_report.html is 5.4 MB and dashboard.html is 753 KB — both committed. CHANGES.md is 216 KB and CLAUDE.md is 55 KB. Between them that is roughly 6.4 MB of generated or append-only text in a repository whose actual source is under 1 MB. Every clone, every diff and every agent context window pays for it. Move generated reports to out/ and gitignore them; split CHANGES.md per season.

Section 04Reliability & operations

Exception handling is hiding your bugs

96 except Exception blocks in server.py, 35 in monitor.py, 14 in odds_monitor.py. A large fraction end in pass. Both send-off defects in Section 01 survived because of this: a NameError that would have been obvious in a stack trace was converted into silence.

The rule worth adopting: catch the specific exceptions you expect (OSError, json.JSONDecodeError, requests.RequestException), and where a broad catch really is needed at a task boundary, use logging.exception() so the traceback lands in the log, and increment an error counter that the dashboard displays. Silence should never be an outcome.

There is no test safety net

Four test_issue*.py files, each a script with hand-rolled PASS/FAIL globals, covering three specific bug fixes. Nothing covers the 26 condition evaluators, none of the 15 API endpoints, none of the ROI mathematics, no CI configuration anywhere in the tree.

  • Convert the four scripts to pytest — they are already structured as assertions.
  • Add a GitHub Action running ruff check and pytest on push. Ruff would have caught both send-off defects in under a second.
  • Golden-file tests for conditions.py: one recorded match JSON per condition type, asserting fired/not-fired. This is the highest-value test suite you can write, because condition semantics are what everything downstream depends on.
  • Property tests on the ROI functions: ROI of an all-losing set is −100%, a push is a push, de-vigged probabilities sum to 1.

Nothing tells you when the monitor stops

If monitor.py starts failing — as it does today on the recovery path — you find out by noticing the absence of Slack alerts. Add a heartbeat: write last_cycle_utc on every successful completion, show a staleness badge on the dashboard, and have a cheap external check post to Slack when no cycle has completed during a scheduled game window.

Polling schedule is fixed, the draw is not

The timer runs every minute from 06:00–12:00 UTC year-round. That burns cycles on days with no fixtures and misses anything outside the window — Vegas round kickoffs, finals scheduling, and Monday night games at the edge. Drive the schedule from the draw API: fetch the round's kickoff times once a day, and poll only from ten minutes before the first kickoff to full time plus a buffer.

Team data is hardcoded

nrl_api.py hardcodes 17 teams across three maps, plus abbreviations and colours in the dashboard. The Perth Bears enter the competition in 2027 and a PNG franchise in 2028. Derive the team list from the draw API with the static table as fallback, so an expansion season doesn't require edits in four files.

Section 05Prediction & ROI analytics

This is the section that matters most for your stated goal, and it is where the problems are most severe. The short version: the model's headline accuracy is an artefact, and the ROI figures are not currently measuring anything you could bet on.

SO-07Send-off

The 98.9% accuracy is target leakage

build_training_data() (ml_model.py:75) computes margin = my_score - opp_score from a completed game record, and the label is 1 if team == winner. The sign of the final margin is the label. The model has learned that the team ahead at full time wins the game.

The README's own feature ranking confirms it: score_margin (+5.2), halftime_margin (+4.1), h2_momentum (+3.7) — the three largest coefficients are all functions of the final scoreline. 99.7% train and 98.9% CV is not a strong model; it is a scoreboard reader.

Why those three numbers say leakage

The coefficients are impossibly large. Features are standardised before fitting, so a coefficient is log-odds per one standard deviation. Exponentiating: score_margin multiplies the modelled odds of winning by ×181 per SD, halftime_margin by ×60, h2_momentum by ×40. One standard deviation of NRL final margin is roughly 13 points. No genuine predictor behaves like that — that magnitude is what a feature looks like when it is the answer rather than evidence about it.

The three features reconstruct the label exactly. score_margin is my_score − opp_score from the completed record, and winner is by definition whoever scored more, so sign(score_margin) is the label once draws are excluded. The other two are not merely correlated with it — from timeline_features.py:82–84:

margin_at_ht = _margin_at_time(score_prog, HALF_SECONDS)
margin_final = _margin_at_time(score_prog, 9999)
h2_momentum  = margin_final - margin_at_ht

So halftime_margin + h2_momentum = final_margin, algebraically, by construction. The model is handed the final margin directly and as an exact two-term decomposition. Its top three features are three views of one number, and that number determines the label deterministically.

Why cross-validation didn't catch it

Cross-validation splits the data into k parts (here 5), trains on k−1 and scores on the held-out part, rotating through all of them. It is the standard guard against a model that has memorised rows rather than learned a pattern.

It cannot detect leakage, because the leaked feature is present in the held-out fold too. The test rows also carry their own final margin, so the rule "predict whoever has the positive margin" transfers perfectly to data the model has never seen. CV is working correctly — it is answering a question about generalisation, not about whether the feature should have existed.

The small gap is itself the tell. Ordinary overfitting shows a wide spread: 99% train against 62% CV. Here it is 99.7% against 98.9% — a gap of 0.8 points. Near-perfect and stable means the model found a rule that genuinely generalises. It did. The rule is "the team that finished ahead won the game."

For calibration: bookmakers land around 68–72% on NRL head-to-head pre-game. An honest in-play model might reach the mid-80s late in a match and considerably less early. Anything above roughly 90% overall should be treated as a leakage alarm rather than a result.

FixTrain on snapshots, not outcomes. For each game, sample the state at (say) every 5 game-minutes: margin at that minute, minutes remaining, conditions fired so far, possession and penalty differentials to date. Label with the final winner. That model can be honestly evaluated, and it will not score 98%. Note also that evaluate_model.py already implements rolling_origin_predictions, brier(), log_loss_metric() and calibration() and is wired into the server — it simply evaluates the frequency and Bayesian models instead. Point that harness at ml_model and most of the evaluation work is already done.
SO-08Send-off

Train/serve skew — the live model sees a distribution it never trained on

predict_winner() builds its feature vector from a live game record, so margin is the current margin, condition flags are whatever has fired so far, and max_unanswered/max_error_streak are partial-game maxima. Training used full-game values for all of them.

The consequence is that confidence_pct has no defensible meaning. A model trained to read final margins, shown a 6-point lead at minute 12, will report high confidence because a 6-point final margin nearly always wins. Every downstream artefact — the predicted_winner_threshold condition, the PW call log, the ROI combo tables — inherits that error.

FixSame as SO-07. Additionally, assert at inference time that the feature vector's provenance matches training (a schema check on which features are "so far" versus "final").
SO-09Send-off

The combo leaderboard is a multiple-comparisons machine

_compute_local_roi_combos() (audit_roi.py:320) enumerates 2 roles × 2 margin signs × 4 selection modes × 3 halves × 5 quarters, ranks the cells by ROI, and defaults to min_calls=1. That is on the order of several hundred hypotheses tested against a few hundred games, with the winners surfaced to a dashboard tab.

With that many cells and that little data, the top of the leaderboard will show a strongly positive ROI whether or not any edge exists — this is what data mining produces by construction. There is no holdout, no correction for the number of tests, no confidence interval, and no minimum sample size. This artefact is the single most dangerous thing in the repository for the goal of improving ROI, precisely because the numbers look specific and authoritative.

FixFour changes: (1) raise min_calls to at least 100 and display the count next to every ROI figure; (2) report a Wilson or bootstrap 95% confidence interval on every ROI cell — most will straddle zero, which is the honest answer; (3) split seasons into discovery (2024–2025) and validation (2026), and only ever promote a strategy that survives the split; (4) apply Benjamini–Hochberg across the grid, or a White reality-check, and show the adjusted significance. Label the tab "hypothesis generation", not "strategies".

The price attached to a call

ROI is computed as a flat 1 unit staked at the odds recorded on the call — _ROI_STAKE = 100.0 against call["moneyline"]. That convention is correct and standard. The problem is which price ends up in that field.

SO-10Send-off

Backfilled calls are priced at the pregame line

_compute_local_roi_combos() reads ml_odds = call.get("moneyline"). In backfill.py that field is populated from the game record's pregame market:

hml = record.get("home_ml")
moneyline = str(hml) if pred_is_home else str(aml)
...
"moneyline":      moneyline,
"live_moneyline": moneyline,   # same value
"bk_moneyline":   moneyline,   # same value

backfill_synth_odds.py states it in its own comment: "Pregame ML from PW call's moneyline field". So for every backfilled game — the bulk of the 514-game history — a call firing at minute 72 is booked at the odds available before kickoff.

This is not a small distortion, and it runs in one direction. It is largest on exactly the calls that look best: a side 14 points up with eight minutes left might be 1.05 live and 1.85 pregame. The signals with the highest hit rate receive the largest fictional price, which is precisely the mechanism that would manufacture an attractive-looking strategy out of nothing.

Live-monitored games are fine — monitor.py captures a genuine live_odds quote at fire time. The history is therefore a mix of correctly-priced and pregame-priced calls in a single ROI series, with no field on the record distinguishing them.

FixAdd an explicit price_source field (live / pregame / synthetic) written at call creation, and report ROI separately by source. Until backfilled calls can be re-priced against a historical in-play line, exclude them from any ROI figure used for a decision. To size the problem now: 
import json
h = json.load(open("game_history.json"))
same = tot = 0
for g in h:
    for c in g.get("predicted_winner_calls", []):
        tot += 1
        if c.get("moneyline") and c["moneyline"] == c.get("bk_moneyline") == c.get("live_moneyline"):
            same += 1
print(f"{same}/{tot} calls priced at pregame odds")
Anything near 100% means the ML ROI column is "pregame price, mid-game signal" throughout.
SO-11Send-off

strict_bk does not filter what its name implies

_filter_strict_bk() (server.py:2977) is documented as removing "PW calls without genuine BK data". It tests:

if c.get("bk_moneyline") or c.get("bk_spread"):
    genuine.append(c)

But backfill.py writes the pregame line into bk_moneyline, so backfilled calls pass the gate. The filter excludes calls with no odds; it does not exclude calls with stale odds. Anyone reaching for the strict-BK toggle to get a trustworthy number is getting the same contaminated series with the odds-less calls removed.

This matters more than an ordinary naming problem, because strict_bk is the control a user would reasonably reach for after being told the data is mixed.

FixFilter on bk_ml_source or bk_spread_price instead. Those fields are written only by monitor.py from a live quote — backfill.py's call builder never sets them (verified: zero occurrences). Then rename the toggle to something that describes what it does, such as "live-priced calls only", and display the surviving sample size next to it.
SB-05Sin bin

Synthetic odds carry no bookmaker margin

A separate problem from SO-10, affecting the synth_* columns rather than the main ML ROI column. synthetic_odds._prob_to_decimal() returns 1.0 / prob — fair odds with zero overround. Australian NRL head-to-head markets typically run about 4–7% overround, and line markets sit near 1.91 / 1.91 (≈4.7%). Every ROI number computed against a synthetic price is therefore overstated by roughly a bookmaker's margin, which is very often the entire difference between a strategy that looks profitable and one that is not.

Compounding it, _decimal_ml_profit() (server.py:2241) returns 90.91 when a price is missing — inventing a −110 American price for absent data. Any backtest that mixes real prices, synthetic prices and this fallback is not measuring a single thing.

FixApply an explicit overround when generating synthetic prices, and tag every stored price with its provenance (real / synthetic / fallback). Report ROI separately by provenance and treat the real-price series as the only one that counts. Never substitute a default price for a missing one — exclude the bet instead.
SB-06Sin bin

The synthetic live line ignores time remaining

compute_synth_spread(margin) is -0.953 × margin + 0.10. A 10-point lead maps to a −9.4 line at minute 3 and at minute 75 alike. Time elapsed is the dominant variable in any live pricing model, and it is absent. compute_synth_moneyline nods at it through a coarse _QUARTER_MULT table only.

The quarters are themselves inherited from the NBA codebase: _quarter_from_minute buckets an NRL match into Q1–Q4 at 20-minute boundaries, but rugby league is played in two 40-minute halves. The buckets don't correspond to anything on the field, so any "by quarter" analysis is cutting the data on an arbitrary grid.

FixMake margin and seconds remaining the two base terms, fitted on your own timeline data — you have 514 games of scoring events, which is enough for a serviceable live win-probability curve. Replace quarters with halves plus a minutes-remaining bucket that matches how the game is actually structured.
SB-07Sin bin

Cross-validation leaks between mirrored rows

Each game produces two rows — home perspective and away perspective — that are near-exact negatives of each other. cross_val_score(model, X, y, cv=5) uses unshuffled KFold, which places a row's own mirror in the test fold while its twin is in training. Even without the leakage in SO-07, the reported CV figure would be optimistic.

FixStratifiedGroupKFold grouped on game_id. For a betting model, go further and use walk-forward validation: train on seasons ≤ N, test on season N+1. That is the only validation that matches how you will actually use it.
SB-08Sin bin

Accuracy is the wrong metric; you need calibration

Betting does not reward picking winners — it rewards knowing how likely a winner is, more precisely than the price implies. A model that is 55% accurate but perfectly calibrated is bettable; a model that is 70% accurate but reports 90% confidence is not. Nothing in the codebase measures calibration.

Also note that predict_winner computes the two sides' win probabilities from two independent forward passes and does not normalise them to sum to 1, so home_win_pct + away_win_pct will generally not be 100.

FixReport log loss and Brier score as the primary metrics, plot a reliability curve (predicted probability decile vs realised win rate), and apply isotonic or Platt calibration as a final layer. Benchmark against three baselines: the de-vigged market price, home-advantage-only, and a margin+time-only logistic. If the model cannot beat the de-vigged market, there is no bet — and that comparison is the single most useful number the dashboard could display.
PE-04Penalty

Pushes are scored as losses

_did_team_cover_spread() (server.py:2255) returns (team_margin + spread_line) > 0. An exact push — margin +6 against a −6 line — returns False and is recorded as a loss rather than a stake return. NRL line markets frequently use whole numbers.

FixReturn a three-state result (win / push / loss) and exclude pushes from both the numerator and the denominator of ROI.
PE-05Penalty

Tied games are classified as "trailing"

margin_sign = "trailing" if score_margin is not None and score_margin <= 0 (audit_roi.py:363). A level scoreline is neither. Given how often NRL games are tied — and that the tied state is a genuinely distinct betting situation — this contaminates both buckets.

FixThree-way: trailing / level / leading.
PE-06Penalty

No closing-line value tracking

Nothing captures the closing price. CLV — whether you consistently beat the price the market settles at — is the fastest reliable read on whether a strategy has real edge. ROI needs hundreds of bets to become statistically distinguishable from noise; CLV gives a usable signal in dozens.

FixAdd a job that snapshots the final pre-kickoff price for every fixture, store it against every recorded call, and make mean CLV the headline KPI on the analysis tab — above ROI.
PE-07Penalty

Flat staking with no bankroll model

_ROI_STAKE = 100.0 everywhere. There is no bankroll, no variance reporting, no maximum drawdown, no risk of ruin. ROI alone cannot tell you whether a strategy is survivable — a 5% edge with high variance and full-Kelly sizing goes bankrupt regularly.

FixModel a bankroll explicitly. Report maximum drawdown and a bootstrapped distribution of final bankroll alongside ROI. See the fractional-Kelly proposal in Section 06.
PE-08Penalty

Backtests assume prices you could not have taken

In-play NRL markets suspend at every try, every conversion and every referee review — precisely the moments your conditions fire. A price recorded in a backfill is not evidence that the price was available to you at that moment, and Australian books apply stake limits that tighten on accounts that win. A backtest with no execution model systematically overstates achievable return.

FixAdd an execution-assumptions layer: a configurable latency between signal and bet, an assumed slippage in ticks, and exclusion of any signal that fires within N seconds of a scoring event. Show ROI with and without those assumptions.

What is missing entirely

Every feature in the model is in-play. There is no pre-game model at all — no team strength rating, no rest days, no travel, no venue effect, no team-list information. That excludes the deepest and most liquid market, and it excludes the place where a well-specified model has the best chance against a line that moves more slowly than an in-play one.

Section 06Forward-testing protocol

Until the pricing and leakage problems are fixed, the historical record cannot answer whether a strategy works. Forward-testing can, and it can start this round.

Forward-testing on paper means recording the bets you would have placed, going forward, at prices you actually observe — with no stake. Same discipline as live betting, no money down. Three properties make it worth more than another cut of the history:

  • The rule is fixed before the data exists. You write the strategy down this week and see what the next 200 signals do. Nothing can be re-cut or re-ranked afterwards, which removes the selection bias that makes the combo leaderboard untrustworthy.
  • The price is real. monitor.py already captures a live quote at fire time. You log the number that was genuinely on screen, not one reconstructed later — which is the exact failure in SO-10.
  • Execution becomes visible. You see how often a signal fires while the market is suspended after a try, and how long a price survives. A backtest cannot show you either.

What to log

One append-only JSONL line per signal, written by the monitor at the moment the call fires:

{"ts", "game_id", "game_minute", "rule_name", "side",
 "price_at_signal", "price_source", "model_prob", "market_prob_devig",
 "ev", "notional_stake", "closing_price", "result", "pnl", "clv"}

closing_price and result are filled in by a later job; everything else is written at signal time and never modified. Append-only matters — a file you can edit is a file you will eventually edit.

Two rules that make it work

  1. Pre-register the rule. Write the exact filter down before the round, and do not add conditions once results come in. If you want to test three variants, declare three and count all three in the significance calculation — testing three rules and reporting the best is the same error as the combo leaderboard, at smaller scale.
  2. Watch CLV before ROI. Whether your price beat the closing line is readable in roughly 30–50 bets; ROI needs several hundred to separate from noise. If you are consistently taking prices worse than the close, no further volume will rescue it — that is the earliest honest signal available to you.

What this needs, concretely

  1. Replace the strict_bk filter per SO-11, then count how many live-priced calls the history actually contains. If it is under about 100, the historical question is settled — there is not enough data to conclude anything, and forward-testing is the only route.
  2. Add a bets.jsonl writer to monitor.py at the point the PW call is created. Perhaps thirty lines.
  3. Add a closing-price snapshot job that captures the final pre-kickoff price for every fixture and backfills closing_price.
  4. Add a paper-trading panel to the dashboard showing, per registered rule: bets to date, mean CLV with a confidence interval, ROI with a confidence interval, and the pre-registration date.

A round or two of NRL gives you the shape of the data. A season gives you an answer. That is slower than reading a number off the existing dashboard, but the existing number is not measuring what it appears to measure.

What to expect from it

This is still measurement, not edge. Paper-testing a signal built on a leaked model will most likely show that the signal does not hold up — which is worth knowing, and considerably cheaper to learn this way than with stakes behind it. The sequence that makes sense is: fix the price filter, fix the model, register a rule, then paper-test it. Running the protocol on the current signal is useful mainly as a rehearsal of the plumbing.

Section 08Proposed capabilities

Ordered by expected value for prediction quality and return, not by effort.

1. A pre-game strength model

The highest-value addition. An Elo or Glicko rating updated on margin of victory, plus home advantage, days of rest, travel (materially relevant for the Warriors, Cowboys and Titans), venue, and — the NRL-specific one — team-list changes. Lists drop Tuesday and late outs move markets significantly; a feature capturing "named halfback/hooker/fullback missing versus last start" is likely to carry real signal that the market prices slowly. This gives you a prior for the live model and a bet in the deepest market.

2. A real live win-probability model

Features: margin, seconds remaining, possession, field position, tackle count in the set, penalty differential, sin-bin state (13-v-12 is a large and quantifiable swing you already detect), and the pre-game prior from (1). Trained on snapshots per SO-07, validated walk-forward, calibrated with isotonic regression. Output: a calibrated probability, not a "confidence".

3. A de-vig layer

Convert bookmaker prices to fair probabilities before any comparison — multiplicative, Shin, or power method, stored alongside the raw price so you can compare methods later. Every downstream calculation should compare model probability to de-vigged market probability. Without this, "edge" is measured against a number that includes the bookmaker's cut.

4. An expected-value engine, replacing the confidence threshold

Today an alert fires when confidence exceeds 65%. That is orthogonal to whether a bet is good. Replace it with EV = p_model × (odds − 1) − (1 − p_model), and require EV above a threshold that accounts for estimation error — a 2% modelled edge is inside the noise of a model fitted on 514 games. Alert on EV, show the model probability, the de-vigged market probability and the gap.

5. Fractional Kelly staking with a bankroll ledger

Quarter to half Kelly, capped at a maximum percentage of bankroll per bet, with a drawdown circuit-breaker that halves stakes after a defined loss and stops entirely at a floor. Kelly on an overconfident probability is how bankrolls die, so the calibration work in (2) is a prerequisite, not an optional extra.

6. A bet ledger and a paper-trading mode

An explicit bets table (schema in Section 03) recording timestamp, market, side, price taken, stake, model probability, de-vigged market probability, EV, result, P&L and closing price. Every new strategy runs in paper mode for a pre-committed number of bets before it is permitted to alert. This converts "the dashboard says +18% ROI" into a record you can audit.

7. Multi-book price capture

You currently prioritise TAB > PointsBet AU > Ladbrokes AU. Capturing several books simultaneously gives you two things: the best available price (which is itself a few percent of edge), and a better estimate of the fair price than any single book provides — the consensus of a de-vigged panel is a stronger benchmark than one bookmaker's line.

8. Market-movement features

odds_monitor.py already tracks live odds. Turn the movement into features: open-to-current drift, velocity, and divergence between books. Line movement is informative about information you do not have, and "the market moved against my model" is a useful suppression signal.

9. Model registry and drift monitoring

Version every model, log every prediction with its full feature vector, and chart rolling log loss by week. Models degrade — rule changes, roster turnover, a new interpretation of the six-again — and you want to see it in the metric rather than in your bankroll.

10. One backtest engine, shared with CI

A single code path used by both the dashboard and the test suite, so the numbers on screen are the numbers the tests assert. Walk-forward by default, confidence intervals on everything, execution assumptions applied, and a hard refusal to report ROI below a minimum sample size.

One honest note on expectations

Everything above improves the measurement, which is the necessary first step. It is worth being clear that better measurement will often reveal that an apparent edge was not there — that is the point of doing it, and it is a good outcome even though it doesn't feel like one.

Sports betting markets carry a structural margin, the great majority of participants lose over time, and Australian bookmakers actively restrict accounts that win consistently — which means an edge that survives everything above can still be hard to realise at meaningful stakes. Treat the CLV metric as your honest scoreboard, size conservatively, and set a bankroll you have decided in advance you are willing to lose. If the numbers ever start driving the stakes rather than the other way around, that's the signal to stop.
