B1Critical Findings

B-01

critical The thread records a residency position that contradicts the stated facts

Comment 2026-08-26T05:51 answers question 4 with "Based in Malaysia — no Polymarket restriction", and the assessment beneath it concludes that "Malaysia-based resolves the jurisdictional question from Rev 2.3 §16".

That is not the position as described to me directly, which is an Australian resident temporarily in Malaysia. Rev 2.3 §16 was rewritten specifically for that case, and its conclusion was the opposite: the eligibility terms exclude persons who reside in or are located in a prohibited locality, the limbs are disjunctive, and temporary presence in Malaysia answers only the second one. Australia is on the restricted list.

To the thread's credit, the later Residency Note asks precisely the right questions — is residency permanent or temporary, and are the identity documents Malaysian or Australian. But that note sits after a comment that has already recorded the favourable answer and built a recommendation on it. In a decision log, the recorded answer is what gets acted on.

The direction of the drift is worth naming plainly: across three statements the position has moved from Australian, to Malaysian, to Australian-temporarily-in-Malaysia, and the issue has settled on the reading most permissive of the project proceeding. That is a normal thing to happen and a bad thing to leave in place.

Fix: Edit the 05:51 comment to state the actual position rather than leaving it to be corrected further down. If residence is Australian, §16 stands unchanged and this remains a gating item requiring Australian legal advice before Phase 2 — not before Phase 4. If residence has genuinely and permanently shifted, say so explicitly with the supporting facts (visa status, domicile, ID documents, intended duration), because that materially changes the analysis and should be recorded once, clearly. Either way, the Betfair path in §16 remains available and removes the question entirely.
B-02

critical Phase 0 cannot yield a valid answer until the calibration defect is fixed

The thread correctly makes Phase 0 the gate: join historical PW fire times to market prices and see whether market_price_at_fire − pw_confidence has positive mass. Both August comments treat this as runnable now, on Crostini, as the first step.

It is not runnable yet, and the reason is Addendum A finding A-01. Phase 0's test statistic has pw_confidence on one side of it. That value is call["pct"], raw and uncalibrated — a grep across both repositories finds calibration measurement but no fitted calibration transform applied anywhere. If PW confidence runs systematically high, Phase 0 returns a positive edge that is entirely an artefact of the confidence scale, and it returns it convincingly.

The shipped #412 Phase 4.10 numbers show what this looks like in practice: 4,478 of 5,588 calls flagged +EV, 80.1%. That figure was produced by the same uncalibrated pct. Phase 0 run today would agree with it, and both would be wrong together.

This inverts the dependency the thread assumes. Phase 0 was positioned as the cheap step that gates everything else; in fact it now sits downstream of a monitoring-side fix tracked under a different issue.

Fix: Fit and version a calibration mapping on settled PW calls before running Phase 0, and run the Phase 0 join against calibrated probabilities. Add the calibration model version to the Phase 0 output so the result stays interpretable when the mapping is refitted. Half a day of work that determines whether the project's central measurement means anything. Cross-link #412 Phase 4.10 to this issue so the dependency is visible from both sides.

B2Chromebook Assessment

Supersedes Addendum A §A2, which assessed a tablet. The revised verdict of "viable for Phase 0–3 with caveats" is close to right, but the setup checklist contains instructions that will not work and one that is destructive.

B-03

high Step 12 recommends a flag that destroys containers

The checklist suggests setting Terminal as a startup app "via chrome://flags/#crostini-reset-lxd-db (experimental)". That flag does not control startup apps. It resets the LXD database on every launch, and is a recovery mechanism for corrupted installations that fail with a dqlite migration error. Enabling it means any container not named penguin is lost whenever the termina VM restarts.

On a device whose defining risk is unexpected reboots, enabling a flag that wipes container state on restart is close to the worst available option.

Fix: Remove step 12's second bullet. There is no supported mechanism to auto-start Crostini on boot — the container starts when a Linux app or Terminal is launched. A .desktop file in ~/.config/autostart runs when the container starts, which does not solve the problem of the container not starting. Treat this as unmitigated (B-06).
B-04

high Auto-updates cannot be disabled as described

Step 6 offers two methods, and neither works on a consumer device. sudo crossystem disable_dev_request=0 relates to developer-mode state, not update policy — enabling dev mode does not stop updates. And chrome://policy is a read-only viewer; DeviceAutoUpdateDisabled is an enterprise policy that requires the device to be enrolled in a managed domain.

This matters because the thread's own risk table rates auto-updates "High — still reboots without warning, but can be disabled in dev mode". The mitigation does not exist, so the residual risk is higher than recorded, and it compounds directly with B-03/B-06: the reboot happens, and nothing brings the container back.

Fix: Re-rate auto-update reboots as unmitigated. If the device can be enterprise-enrolled, update scheduling becomes available and is worth doing. Otherwise plan around reboots rather than trying to prevent them.
B-05

high The stale Singapore recommendations are still live in the thread

Three May comments recommend Singapore hosting — "Vultr Singapore at $12/month is the sweet spot", the Oracle free tier deep-dive with Singapore as the locked home region, and the setup steps that select Singapore at signup. Rev 2.3 finding C-06 established that Singapore has blocked Polymarket since January 2025, and the July comment records that, but the May comments remain unamended above it.

The specific trap: the agreed fallback plan is "escalate to a VPS if Crostini proves unreliable". The thread's VPS recommendation is Singapore, and the Oracle path involves a home region that cannot be changed after signup. A rushed fallback under pressure would land on a permanently wrong region.

Fix: Edit the May comments with a struck-through correction pointing at C-06, and record the fallback region decision now rather than at the moment it is needed. Rev 2.3 §16 has the revised comparison.
B-06

high Crostini auto-start is correctly identified as the top risk and left unsolved

The thread names it: "If the Chromebook auto-updates and reboots at 3am, the bot stays dead until someone opens the Terminal app." That is the right conclusion, and with B-03 and B-04 removing both proposed mitigations, it is the binding constraint on the whole approach.

NBA windows span UTC 16:00–08:00, which is overnight in Malaysia. A reboot at hour three of a sixteen-hour window means the remaining thirteen hours are lost, and the dead-man switch alerts to a phone that is next to a sleeping operator.

Fix: Accept it explicitly rather than engineering around it. For Phase 0 and 1 it is genuinely fine — batch work re-runs. For paper trading it is the thing that makes the results non-comparable to live, so record reboot events as first-class data (B-07). Do not carry it into any phase holding positions.

Medium and low

#SevFindingChange
B-07mediumThe proposed gate is "uptime ≥90% during game windows". Uptime is the wrong statistic — what breaks a paper-trading sample is non-random gaps, not their count. A Chromebook that sleeps at a consistent local hour, or drops WiFi under a specific load, produces missing signals that differ systematically from captured ones. 95% uptime with correlated gaps is worse than 85% random.Test whether downtime correlates with signal characteristics — hour of day, quarter, market, consensus type. Report that alongside the uptime percentage.
B-08mediumStep 13 suggests sudo iw dev wlan0 set power_save off inside Crostini. The container has no direct access to the host wireless interface — it sees a virtual ethernet device. The command will not find wlan0.Remove. WiFi power management is a ChromeOS host concern not reachable from the container. The USB ethernet adapter is the real fix and is already recommended.
B-09mediumStep 8 says to allocate 2–4GB RAM to the container. Crostini exposes a disk-size control, not a RAM allocation — memory is managed dynamically by the VM.Correct the instruction. The disk figure matters more: 10GB is suggested, but the thread's own resource table lists a 4.9GB ESPN cache and 2.5GB of backups. Confirm whether the Chromebook runs the bot only or the monitor too — the two comments disagree.
B-10mediumThe issue body specifies py-clob-client-v2 as "purpose-built for programmatic trading", but the ARM verification table and the setup instructions both use py-clob-client. Different packages, potentially different dependency trees.Settle which SDK, then re-run the ARM check against that one. The v2 tree may not match what was verified.
B-11lowThree phase-numbering schemes coexist: the original body's Phase 1/2/3 (relay/bot/risk), Rev 2.3's Phase 0–5, and "Phase A/B" in the clarification answers. The August comments mix all three.Adopt Rev 2.3's numbering throughout and edit the body, or the go/no-go gates will be argued about later.
B-12lowChromeOS is migrating Linux support to a new backend ("Baguette") as the default from M147, with multi-container support and ansible-based setup deprecated.Not blocking, but a long-lived Crostini deployment sits on a platform that is changing underneath it. Another reason not to build anything load-bearing on it.

B3Correction to Addendum A

corrected ARM compatibility — the thread's verification beats my caution

Addendum A §A2 flagged that "the Polymarket path pulls in native signing dependencies (eth-account, coincurve/secp256k1) where ARM wheel coverage is less reliable and source builds may be needed."

The 2026-05-12T04:51 comment tested this properly and found the tree is pure Python apart from bitarray, which ships prebuilt aarch64 wheels. That is a real verification against my speculation, and it wins. The concern is withdrawn.

One caveat that keeps it honest: the check should be re-run against whichever SDK is finally chosen (B-10) and against pinned versions at install time, since dependency trees shift — newer eth-account releases have pulled in C extensions that older ones did not.

The Chromebook decision is smaller than it looks

Steps 2 through 5 are the ones that decide this project, and every one of them is batch analysis that runs fine on the Chromebook — or on any machine, including the AU server already running 24/7. The reliability debate only becomes load-bearing at step 8, and only matters at step 9, which the thread already correctly rules out.

So the honest framing is that the hardware question has been given more weight than it can carry. Using existing hardware to save VPS cost during a testing phase is a perfectly reasonable call, and the phase-viability table in the thread already lands in the right place. The two critical findings above are worth considerably more attention than the Crostini setup checklist.

One thing worth watching in how this issue is developing

Between the August comments, the assessment moved from "not recommended" to "viable for Phase 0–3 with caveats", and the residency position moved to the reading most favourable to proceeding. Both movements may be correct on the facts. But they moved in the same direction within the same hour, and the supporting details in each — the update-disabling method, the startup flag, the residency answer — do not hold up individually.

That pattern is worth noticing early, because the parent review's central argument is that this project's value lies in finding out cheaply whether an edge exists. A decision log that resolves ambiguity toward continuing is the mechanism by which that value gets lost.
