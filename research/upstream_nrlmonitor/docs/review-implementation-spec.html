01Review overview

Two independent code reviews identified overlapping patterns across the shared codebase. This spec consolidates all findings into a single prioritised implementation plan.

Key conclusions

  • 4 silent runtime defects across both repos — all scope errors swallowed by broad except Exception handlers, all findable by a one-second lint run.
  • Security baseline is inconsistent — fixes exist in one repo but not the other. NBA leaks all secrets via /api/config; NRL has path traversal on backup deletion. Both bind to all interfaces with wildcard CORS. The tailnet boundary contains these; it does not remove them.
  • NBA model is sound; NRL model has target leakage — NBA uses point-in-time features, NRL trains on the final scoreline. NBA has walk-forward/Brier/calibration infrastructure that isn't connected to the sklearn model.
  • NBA ROI figures are approximately 98% backfill-derived and therefore priced at pregame odds for mid-game signals. Measured, not estimated — see Section 02.
  • 70–93% code overlap in infrastructure modules — clean boundary between shared (backup, trend, outcomes, synthetic odds) and sport-specific (conditions, ML model). Fixes flow in both directions and land in only one repo.

Live staking is currently on compromised NBA figures

Stakes are being placed on the numbers this system produces. For NBA, 1.7% of calls carry a genuine at-fire price; the rest are booked at the pre-kickoff line. That bias runs in one direction and is largest on the signals that look strongest — a side well ahead late is short live and long pregame, so the highest-hit-rate strategies receive the largest fictional prices.

The implication is narrow and specific: NBA ROI figures do not currently support a staking decision. WNBA and NRL have workable live-priced subsets and can be assessed on those, at reduced sample size. Phase 4.1 is two hours of work and resolves which figures are which — worth doing before the next slate rather than after.

With the network exposure corrected, this is now the highest-priority item in the document.

What the reviews got right that's worth preserving

  • NBA: point-in-time ML features (no leakage), parity_check.py (live vs replay assertion), evaluate_model.py with walk-forward/Brier/calibration, FEATURE_SCHEMA_VERSION check, backup name validation on the delete endpoint.
  • NRL: config secret masking on /api/config, separate API client module (nrl_api.py), continuous odds monitoring thread (odds_monitor.py), timeline feature extraction (timeline_features.py).
  • Both: WAL + atomic writes + snapshot/restore, two-phase backfill, condition evaluator architecture, PW changelog tracking.

03Code defects

All four critical defects are the same class: a variable referenced outside its scope, caught by a broad exception handler, resulting in silent feature failure.

Critical NBA SO-01: _sl_game_ids out of scope

monitor.py:2796 reads _sl_game_ids — a local of main() assigned at line 3200. build_pregame_snapshot_for_event() is a separate function and cannot see it. NameError swallowed by except Exception as _oa_exc.

Impact: pregame odds fallback silently fails for every game where ESPN doesn't supply prices. Summer League games always affected.

Fix: pass sl_game_ids as a parameter. verified There is exactly one call site (monitor.py:3445), inside main() where the variable is in scope — so this really is a two-line change.

Critical NBA SO-02: _pw_half_quarters out of scope

server.py:3528 reads _pw_half_quarters — a local of build_history_list_payload() assigned at line 3842. _history_matches_filters() is a separate function.

Impact: half filter (H1/H2/OT) on the game history endpoint returns a 500.

Fix: make the mapping a module-level constant; resolve inside _history_matches_filters from the filters dict. Note the near-identical check at server.py:4171 is correct, because _pw_stat_call_matches is nested inside build_history_list_payload and picks the name up as a closure — do not "fix" that one.

Critical NRL SO-01: now used before assignment corrected in rev 2

monitor.py:1246 assigns now = datetime.now(timezone.utc). Because the assignment exists, Python treats now as local for the whole of main(), so earlier reads raise UnboundLocalError.

The affected sites are exactly four: 1179, 1192, 1208, 1230. Revision 1 also listed 234, 270, 271, 291, 316, 335, 867 and 903 — main() spans 998–2305, so those lines are inside _recover_missed_game, _append_recovery_log, _record_pw_call and _poll_live_odds, where now is an explicit parameter. That code is correct and must not be changed.

Impact: auto-recovery silently fails every cycle; missed games are never recovered. Lines 1179 and 1192 are guarded only by except (ValueError, TypeError), and UnboundLocalError subclasses NameError, so if a recovery_checked_* key ever reaches .alert_state.json the whole cycle terminates uncaught.

Fix: hoist now = datetime.now(timezone.utc) to the top of main() and remove the line 1246 assignment. Leave every helper signature alone.

Critical NRL SO-02: new_config undefined corrected in rev 2

server.py:4817 — not 4831, which is a bare try: — reads new_config.get("backup_retention", {}). The local variable is payload; new_config appears exactly once in the file. NameError caught by except Exception: pass.

Impact: pre-config-save snapshot pruning has never run. runtime_backups/ grows without bound.

Fix: change new_config to payload.

04Security

The dashboards are tailnet-only and not publicly reachable. That contains the blast radius but does not eliminate it — the wildcard CORS header is exploitable from any browser that can route to the service, and the browsers in question are inside the tailnet by definition.

Confirmed network topology

Dashboards on NBA 8899, WNBA 8900, NRL 8898, served on 8444/8445/8446 as tailnet-only. Tailscale Funnel is configured on 443 only, proxying to 127.0.0.1:8788 — a separate service, out of scope for these reviews. Nothing in either repository is reachable from the public internet.

High Wildcard CORS makes the secrets readable by any page a tailnet browser loads

send_json() sets Access-Control-Allow-Origin: * on every JSON response in both repos:

def send_json(self, code, data):
    ...
    self.send_header("Access-Control-Allow-Origin", "*")

That header authorises a cross-origin read of the response body, so an arbitrary web page can fetch() /api/config and read the result. Two routes, neither requiring Funnel:

  • Localhost. If any browsing happens on a machine running a dashboard, fetch("http://127.0.0.1:8899/api/config") from any loaded page succeeds. Localhost port probing from JavaScript needs no hostname knowledge.
  • Tailnet. From a browser elsewhere on the tailnet, an attacker needs <machine>.<tailnet>.ts.net plus the port. Tailscale provisions Let's Encrypt certificates for those names, so the hostname is discoverable via Certificate Transparency logs; 8444–8446 is a short scan.

Both routes require the victim's browser to be on the tailnet, which is why this is High rather than Critical. It is not inert, and the fix is deleting one header.

Fix: remove the wildcard header from send_json() and do_OPTIONS(). The dashboard is same-origin and does not need it. Phase 2.1 — ten minutes, highest value per line in the document.

High NBA: /api/config returns all secrets unmasked

NBA GET /api/config returns the raw config file with slack_bot_token, openclaw_token and odds_api_key. NRL masks two of three but leaks odds_api_key. The static file handler serves config.json directly in both repos — NBA's containment check passes because the file sits inside the script root.

On its own this is a tailnet-internal disclosure. Combined with the CORS finding above it becomes remotely readable by any page a tailnet browser visits, which is why the two should be fixed together.

Fix: (1) shared SECRET_KEYS constant for mask on GET and re-merge on POST; (2) allowlist the static handler to dashboard.html and known assets; (3) move secrets to environment variables so neither route can leak them. Phase 2.2, 2.5, 2.6.

Critical NRL: path traversal on backup delete; NBA: restore unvalidated

NRL /api/recovery/delete-backup joins a user-supplied name to the backup root and calls shutil.rmtree with no os.path.basename() and no containment check. NBA's delete validates (".." in name or "/" in name) plus a league-ownership check, but its restore endpoint passes the name through unvalidated.

This stays Critical despite the tailnet boundary. A destructive POST needs no readable response, so the wildcard CORS header plus absent CSRF protection is sufficient — a page loaded in a tailnet browser can fire the request blind and delete directories or overwrite live history.

Fix: shared _safe_backup_name() helper — basename(), then verify os.path.realpath() resolves under the backup root. Apply to delete, restore and prune in both repos. Phase 2.3.

05Analytics & ML

The NBA model is methodologically sound but unvalidated. The NRL model has target leakage. ROI computation has systemic issues in both repos, now quantified.

NBA model: no leakage

build_training_rows() uses score_margin_at_fire and quarter_elapsed_pct — the state at the moment the condition fired, not the final scoreline. This is correct. The NRL model uses the final margin as a feature against a "did they win" label, which is why it reports 98.9% and means nothing.

Critical NRL: ML model target leakage (98.9% is an artefact)

score_margin (final) is a feature and winner is the label, so sign(score_margin) is the label. Worse, halftime_margin + h2_momentum = final_margin exactly — timeline_features.py:82–84 defines h2_momentum = margin_final − margin_at_ht — so the model receives the final margin directly and as an exact two-term decomposition. Standardised coefficients of +5.2, +4.1 and +3.7 correspond to odds multipliers of ×181, ×60 and ×40 per standard deviation.

Cross-validation cannot detect this: the held-out rows carry the leaked feature too, so the rule transfers perfectly. The narrow 99.7/98.9 train–CV gap is itself the tell — ordinary overfitting produces a wide gap.

Fix: train on time-sliced snapshots (state at each 5-minute interval, labelled with the final winner), porting the NBA score_margin_at_fire approach. Use StratifiedGroupKFold on game_id — NRL emits mirrored home/away rows that leak across ungrouped folds.

Critical NBA: sklearn model has no validation

The walk-forward/Brier/calibration harness in evaluate_model.py evaluates the frequency and Bayesian models. The sklearn model driving PW predictions has no cross-validation, no holdout and no calibration measurement — _fit_variant() reports sample_size and positive_rate.

Fix: point the existing harness at ml_model via a fit_fn adapter, grouped on game_id. Publish Brier, log loss and the calibration table for all models side by side, with the de-vigged market probability as a fourth column. Note the training rows are one-per-condition-fire, so a game contributes many correlated rows — ungrouped folds will inflate the result.

06Backfill & data pipeline

Audited in revision 4. The pipeline is more careful than expected in three places and has one footgun that can corrupt the counts everything else is measured against.

High NRL backfill can duplicate records; NBA's cannot new

NRL gates its duplicate guard on an opt-in flag (backfill.py:886):

if skip_existing and match_id in existing_ids:
    skipped += 1; continue
...
history.extend(new_records)        # appends regardless

existing_ids is seeded from history at line 843 but consulted only under skip_existing. NBA's equivalent guard (backfill.py:2421) is unconditional, and monitor.append_game_record() dedupes correctly in both repos.

So any NRL backfill run omitting --skip-existing appends a second record for games already present — including live-monitored ones. The result is one record with genuine at-fire prices and one with pregame prices for the same match, inflating every count and double-counting the ROI series. The documented invocation at the head of the file does include the flag, so this is a footgun rather than a certainty.

Fix: make the guard unconditional (3.8), and audit the existing history for duplicate match_id before any analytics work (4.0). Note NRL's backfill write path also bypasses append_game_record() entirely — its own history.extend + os.replace — so backfilled records never reach the WAL (6.14).

Medium --pw-force stamps a historical version label on calls produced by today's code new

Backfill resolves pw_version from the game's date (backfill.py:496, stamped at 817) via pw_trend.resolve_pw_version — correct behaviour, and better than stamping today's version. But --pw-force regenerates the calls using the current implementation, so a call can read pw_version: v1.0 while having been produced by logic that did not exist then.

The label tracks configuration, not code. Any trend analysis segmented by pw_version is therefore comparing labels rather than implementations.

Fix: add a separate code or artefact version to the call record — model_schema_version from ml_model.SCHEMA_VERSION, plus a git short SHA where available (4.12, 6.15).

The pregame pricing is structural, not a bug

backfill_odds.py fetches from one to three days before kickoff and matches events to fixtures. That is what the Odds API's historical endpoint provides. Two consequences:

  • Backfilled records can never carry at-fire prices without a different data source. The measured live-priced counts (262 / 1,359 / 844) are a ceiling on the existing history, not something a smarter reprocessing pass can raise.
  • Any plan that assumes historical ROI can be repaired is mistaken. It can only be correctly labelled, which is what 4.0–4.2 do, and then largely set aside — hence Phase 5.

Three things the pipeline gets right

  • Lookahead guard (#40). _prior = [r for r in history + new_records if (r.get("kickoff_utc") or r.get("ts") or "")[:10] < game_date] — frequency and edge lookups cannot see games at or after the one being processed. This is the mistake most retrospective sports models make, and it was avoided deliberately.
  • pw_version resolved from the game date rather than from the current config, so backfilled calls carry the version in force at the time.
  • backfill_synth_odds.py is namespaced and idempotent — writes only synth_* fields and skips where already populated, so it cannot clobber a live-captured price. A pre-backfill snapshot is also taken before the canonical write.

The discriminator that already exists

Every PW call already carries a reliable provenance flag, set at creation in both repos:

backfill.py:815    "synthetic": True
monitor.py:901     "synthetic": False

And server.py:2393 already derives from it, with filtering support wired at 2464 and 2474:

if not c.get("source"):
    c["source"] = "backfill" if c.get("synthetic") else "live"

The defect is therefore narrower than revision 2 described: _compute_local_roi_combos reads call.get("moneyline") without ever consulting synthetic. This is a better discriminator than the bk_ml_source filter recommended in revision 2, because it is set on every call rather than only where a live quote happened to be captured — and it makes 4.1 and 4.2 substantially cheaper.

09Data & process transition

The plan lists changes; this section covers moving the existing data and running systems through them. Several items touch data that cannot be un-touched.

Before any analytics work: the duplicate decision

If the NRL history contains duplicate match_ids, every figure in Phase 4 is computed on inflated data. The dedupe rule is not obvious, because neither record dominates: the live record has genuine at-fire prices and possibly a partial timeline; the backfilled record has complete match data from cache.

The likely answer is a merge rather than a pick — live PW calls and prices, backfill conditions and timeline. Decide and document the rule before writing anything, because the collapse is one-way.

Derive rather than migrate

price_source needs no migration write — it is derivable on read from call["synthetic"]. Prefer that to rewriting a 5,248-game JSON file.

Every mass rewrite of game_history.json is a risk event, particularly given the unqualified .tmp path (3.6) and a monitor that may be running concurrently. Where a write is genuinely required:

  1. Stop the monitor timer.
  2. runtime_backup.snapshot_runtime_files(label="pre-migration").
  3. Migrate.
  4. Verify record counts and per-season totals against the snapshot.
  5. Restart, and confirm the next cycle appends normally.

The model cutover

Asset already in place: NRL's ml_model.py defines SCHEMA_VERSION and load_model() rejects an artefact whose schema does not match (line 225). Bumping it as part of the leakage fix will refuse the old model rather than silently loading it. NBA has the equivalent in FEATURE_SCHEMA_VERSION.

Gap: the version is stamped on the model, not on the call. Historical calls carry only pw_version, which is config-derived. There is therefore no way to segment the accuracy or ROI series by which model produced a call, so pre-fix and post-fix calls will sit in one undifferentiated series and any "accuracy improved" reading after 4.6 will be uninterpretable.

  • Add model_schema_version to the call record at cutover (4.12).
  • Treat the pre-fix series as a closed set. Do not regenerate historical calls with the new model — that is hindsight, not repair.
  • Reset the headline model-performance series at the cutover date and label it as such on the dashboard.

Two series must start empty

  • bets.jsonl must not be seeded from history. The whole value of pre-registration (5.0) is that the rule predates the data. Backfilling the log would reintroduce precisely the selection bias it exists to remove. It is tempting, because it would produce a usable sample immediately — that is the reason not to.
  • CLV is forward-only. Closing prices for past fixtures are not recoverable at reasonable cost, and a mix of real and approximated closes is worse than a short honest series. Accept a start date.

All three services are live. The systemd units impose constraints the earlier revisions did not account for — in particular, the deployable unit is larger than one league.

High NBA and WNBA cannot be deployed independently new

Disaster recovery: one host, untested backups new

Everything — three leagues, all history, the models, both configs — lives on a single machine, and the off-host copy is an rsync to Google Drive that has never been restore-tested. A backup that has never been restored is a hope, not a control; rsync in particular fails quietly (auth expiry, excluded paths, one-way deletes) in ways that only a restore reveals.

  • Restore drill (2.10): restore the Drive copy to a scratch directory, verify record counts, config presence and model loadability against production, and time it. Repeat quarterly. First run this week — before any data-touching phase, since the snapshot-restore rollback class in this section silently assumes backups work.
  • Coverage check: confirm the rsync includes the gitignored files — game_history*.json, model.pkl, config.json, config-wnba.json, the state files — which are precisely the files git cannot recover. Confirm deletions don't propagate (--backup or versioned destination).
  • DR runbook: one page — reinstall, clone, venv, restore from Drive, re-enable units, verify heartbeat — with a stated recovery-time objective. Mid-season, a day of outage is missed games and missed live prices that cannot be re-captured.

Observability is the precondition, not the polish

Dashboards run Restart=always with RestartSec=5, so a bad deploy produces a silent crash loop whose only symptom is the absence of Slack alerts — precisely how the now defect survived a season. The heartbeat has therefore moved from 6.7 to 1.7 and should land before any in-season deploy. It is half a day and it is the safety net for everything else in this plan.

Three silent failure modes the heartbeat alone does not catch:

  • Dead alert path. A revoked Slack token or webhook failure is indistinguishable from a quiet slate. Fix: a daily "monitor alive, N games watched, M alerts sent" summary message — silence then becomes a signal — plus alert-send failures incrementing a visible error counter (1.7).
  • Exhausted Odds API credits. At 20k credits/month, a careless re-backfill can consume the budget and silently stop live price capture — corrupting exactly the clean dataset Phase 5 exists to build. Fix: remaining credits in the heartbeat payload with a threshold alert at 25% (1.7); budget re-fetch jobs explicitly.
  • Upstream schema drift. ESPN and NRL.com endpoints are unofficial and contract-free; a renamed stat key degrades conditions quietly — the sendOffs stub shows it has already happened once. Fix: a lightweight ingest validator that alerts when expected keys go missing from live responses, and a daily canary parse of a golden sample (3.10).
  • Dead host. The heartbeat lives on the machine it monitors. Fix: an external watchdog — a free ping-expectation service or a cron on any second machine — that pages when the heartbeat stops arriving (3.9).

Also worth checking before it becomes a mystery: the monitor units set MemoryMax=2G, against a 5,248-game history loaded whole plus a ConditionEdgeStore built per request. If that ceiling is reached, systemd kills a oneshot cycle with no application-level trace. Record current RSS as a baseline.

Shadow mode for anything that changes alerting

4.10 replaces a 65% confidence threshold with an EV test, and 4.6 replaces the NRL model outright. Both change which alerts fire, in an unknown direction and magnitude. Deploying either straight into a live season means discovering the answer in Slack.

Dual-decision period: compute the new decision, write it to bets.jsonl with the rule ID, and continue alerting on the old rule. Compare volumes and hit rates for a defined period — a fortnight, or 100 signals, whichever comes first — then cut over. This is also exactly the data Phase 5 wants, so the shadow period is not lost time.

Staging on a copy

There is no staging environment. 4.0 (dedupe), 4.5 and 4.6 (model work) should not run first against production data. The snapshot machinery plus --use-cache makes a scratch run cheap:

  1. Copy game_history*.json, the state files and espn_cache/ to a scratch directory.
  2. Run the change there with --use-cache and --dry-run where available.
  3. Diff record counts, per-season totals, call counts and accuracy figures against the original.
  4. Only then apply to production, following the migration steps in Section 09.

Odds API credits: odds_api.py tracks rate-limit state and remaining credits. Any re-backfill consumes quota, and exhausting it mid-season blinds the live odds poller. Require --use-cache on re-runs and check remaining credits before any historical fetch.

Three gates before training proceeds, all bypassed by --force: an enabled flag in config, a staleness check (model age ≥ interval − 1h), and a SHA-256 hash of game_history.json (skip if unchanged). All three gate on whether to bother, none on whether the result is any good.

High Train-on-schedule with no quality gate, no comparison, no rollback new

When the interval elapses and the hash has changed, ml_model.train_and_save() fits on everything and the artefact goes live immediately. There is no pre-train evaluation of the current model on recent data, no post-train comparison of new against old, no holdout protection, and no rollback if the new model is worse. evaluate_model.py computes Brier, log loss and ECE — but on demand, disconnected from the pipeline.

Two concrete consequences today:

  • NRL retrains reinforce the known leakage weekly. Every Thursday 13:00 UTC the leaked model is re-fitted on the same leaked features and redeployed. Nothing improves and the artefact date freshens, which makes the model look maintained.
  • A bad data batch deploys silently. Summer League contamination, a schema drift upstream, or a duplicated history (Section 06) flows into the next weekly artefact with no tripwire between data and live alerts.
Fix (7.1, staged): (a) immediately — stop the NRL scheduled retrain (1.8): a stopped clock beats one that re-injures itself weekly; the deployed artefact keeps serving. (b) Champion–challenger: the runner trains a challenger, evaluates champion and challenger on the trailing window via the existing evaluate_model.py metrics, and promotes only on improvement (log loss, with a no-worse guard on ECE); otherwise it keeps the champion and alerts. (c) Archive artefacts — model_YYYYMMDD.pkl plus metrics JSON, so rollback is a symlink move. (d) Wire the decision into the heartbeat: "retrained: promoted/held, champion log loss X vs Y".

This section and Phase 7 are deliberately coupled: the champion–challenger harness built here is the same machinery the drift tripwire (7.2) and the blend evaluation (7.5) run on. Build it once.
