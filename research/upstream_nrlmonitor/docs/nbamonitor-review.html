Engineering, analytics & parity audit · 26 July 2026

NBAMonitor

A review of the NBA/WNBA monitor on its own terms, and of what the two codebases are costing each other by being two codebases.

51 Python files · 38,381 lines monitor.py 5,862 · server.py 6,979 · outcomes.py 4,326 dashboard.html 1.09 MB Companion to the NRLMonitor review

This is the more mature of the two projects, and in several places it is genuinely good. The prediction model uses point-in-time features rather than final scores, so it does not have the leakage that invalidates the NRL model. evaluate_model.py implements rolling-origin validation, Brier score, log loss and calibration bins. parity_check.py replays live-monitored games through backfill and asserts the conditions match. That is real methodological discipline and it is rare.

But the good machinery is pointed at the wrong things. The walk-forward and calibration harness evaluates the frequency and Bayesian models; the scikit-learn model that actually drives predictions is fitted on all rows with no cross-validation, no holdout and no calibration measurement at all. The parity harness is quietly weakened by a functools.partial that is built and never called.

Two runtime defects of exactly the same class as the NRL one. A helper references a variable that lives in main(); another references one that lives in a sibling function. Both raise NameError, both are swallowed, both are found by a one-second lint. Three of these across two repositories is a pattern, not bad luck.

Security is worse here than in NRL. GET /api/config returns the configuration file unfiltered — Slack token, OpenClaw token and Odds API key included. The NRL fork masks two of the three. Conversely, NRL's backup deletion is traversable and NBA's is not. Fixes have flowed in both directions and landed in only one repository each time.

The parity question answers itself in the numbers. Across 17 shared module names, the infrastructure layers share 70–93% of their function names while the sport-specific layers share 6–17%. That gap is the seam where a shared library should be cut, and it is unusually clean.

Section 01Code defects

Confirmed against source. Line numbers refer to the archive as shipped.

SO-01Send-off

Pregame odds fallback is dead — _sl_game_ids is out of scope

build_pregame_snapshot_for_event() (monitor.py:2723–2869) reads _sl_game_ids at line 2796 to decide whether a game should be priced against the Summer League sport key. _sl_game_ids is a local of main(), assigned at line 3200. It is not a module global and it is not a parameter, so the reference raises NameError.

_sl_sport = "basketball_nba_summer_league" if str(game_id) in _sl_game_ids else None
#                                                              ^ local of main()

The call sits inside try: … except Exception as _oa_exc:, so the failure is logged and swallowed. The practical effect: whenever ESPN does not supply moneyline or spread for a fixture — which is exactly when the Odds API fallback is supposed to earn its keep — the fallback never runs and the pregame snapshot is written with "--" prices. The other nine call sites (3521, 3565, 4428, 4585, 5016, 5355, 5509, 5660) are inside main() and work correctly, which is why this looks fine on a read-through.

FixPass sl_game_ids as an argument to build_pregame_snapshot_for_event(), or hoist it to a module-level cache populated once per cycle. Then check the log for _oa_exc lines to see how long this has been silently failing.
SO-02Send-off

The half filter on game history raises NameError

_history_matches_filters() (server.py:3197–3594) references _pw_half_quarters at line 3528. That name is a local of build_history_list_payload(), assigned at line 3842:

_pw_half_quarters = {"H1": ("Q1","Q2"), "H2": ("Q3","Q4"), "OT": ("OT","2OT")}.get(pw_half, ())

The guard is if pw_half and …, so the failure only fires when a user actually selects H1, H2 or OT. build_history_list_payload then calls _history_matches_filters in a list comprehension at line 3890 and the exception surfaces as a 500 from the endpoint.

Worth noting why this one hid so well: the near-identical check at line 4171 is fine, because _pw_stat_call_matches is nested inside build_history_list_payload and picks the name up as a closure. Two lines of nearly identical code, one broken, one correct, differing only by nesting depth.

FixMake the mapping a module-level constant and resolve it inside _history_matches_filters from the filters dict it already receives. Add an endpoint test that exercises every filter parameter once — that class of test would have caught this the day it shipped.
SB-01Sin bin

The parity harness is weakened by a partial that is never invoked

backfill.py:1119 builds _check_b2b = functools.partial(check_b2b_from_index, …) and never calls it. The comment above it states the intent precisely: "Use history-derived B2B index when available (replay/parity mode); falls back to live scoreboard check_b2b for live runs."

Because the partial is discarded, replay mode uses the live back-to-back path regardless. That matters more here than a normal dead local would, because parity_check.py exists specifically to assert that replayed conditions match live-recorded ones. Any condition sensitive to back-to-back state can now diverge between live and replay, and the harness built to detect divergence is the thing being fooled.

FixWire _check_b2b into the condition evaluation call, then re-run parity_check.py over a sample of games and see whether the parity numbers move. If they do, that also tells you how much of the historical backfill was replayed with the wrong B2B semantics.
PE-01Penalty

An abandoned FG% delta feature

conditions.py:693 initialises prev_fg_pct = None ahead of the tick-snapshot loop and never assigns or reads it again. This is the same shape as the half-written PBP fallback in the NRL evaluate_red_card: a feature started, left in place, and indistinguishable from working code on a skim.

FixFinish it or delete it. If a field-goal-percentage delta is wanted as a momentum signal it is a reasonable one — but half-present is worse than absent.
PE-02Penalty

Twelve f-strings with no placeholders in the strategy comparison tool

compare_edge_gate.py lines 201, 206, 217, 267–270, 274, 315, 316, 320 are all f"…" literals containing no {}. In a reporting script whose entire job is printing computed comparisons, that is a strong signal that interpolation was intended and the braces were lost — the output lines are probably printing labels where they should be printing numbers.

FixRead those lines against their surrounding context and restore the intended values. Then run the tool and check its output actually varies with the data.
PE-03Penalty

Dead locals concentrated in the replay path

pbp_replay.py alone has five: is_home (207), fired_run_anchors (214), run_anchor (247), last_pred_team_id (947), prior_for_first (976). Two of those names — fired_run_anchors and run_anchor — suggest run-detection bookkeeping that was intended to prevent duplicate firing and now does not exist.

Elsewhere: backfill_pw_calls.py:700 _edge_frontier; outcomes.py:2379 _MATRIX_DIMS; backfill.py:1670 _e, :2342 yyyymmdd; monitor.py:1522 _winner_id, :2289 winner_abbr, :3331 just_started; server.py:4551 away_id; evaluate_pw_improvements.py:210 incorrect; analyse_bk_odds.py:1082 quarter_mins; evanalytics.py:248 an unused global declaration.

FixTriage the replay ones by hand — they may indicate missing logic — and let a linter clear the rest.

Section 02Security

SO-03Send-off

GET /api/config returns every secret you have

server.py:4653:

if path == "/api/config":
    with open(CONFIG_FILE) as f:
        self.send_json(200, json.load(f))   # no filtering at all

That returns slack_bot_token, openclaw_token and odds_api_key to any caller. The NRL fork strips two of the three at this exact endpoint — the masking logic exists, it was written, and it never came back to this repository.

The static handler is a second route to the same data. It correctly resolves and containment-checks against the script root (server.py:6540), which is better than NRL's implementation — but config.json lives inside the script root, so GET /config.json passes the check and returns the file.

FixRotate all three credentials on the assumption they are exposed. Add a shared SECRET_KEYS constant, strip on GET and re-merge on POST. Allow-list the static handler to known assets. Then move secrets to environment variables so neither route can leak them.
SO-04Send-off

No authentication, bound to all interfaces, wildcard CORS

server.py:6974 binds ("0.0.0.0", PORT). Every response carries Access-Control-Allow-Origin: * (4633, 4642). There is no token, session, or Origin check anywhere in the file. The POST surface includes config rewrite, backup restore, backup delete, prune, cloud-backup execution and ML training.

With no CSRF protection and a wildcard CORS policy, any page in a browser on the same network can drive those endpoints.

FixSame prescription as NRL: drop the wildcard header, add auth, validate Origin on state-changing requests, and reach it remotely over Tailscale or an authenticating reverse proxy rather than an open port.
SB-02Sin bin

Restore is unvalidated while delete is — inconsistent hardening

/api/recovery/delete-backup (server.py:6620) does this properly:

if not name or ".." in name or "/" in name:
    errors.append("{}: invalid name".format(name)); continue

…and adds a league-ownership check on top. /api/recovery/restore (server.py:6586) takes body.get("backup", ""), strips whitespace, and passes it straight to restore_from_backup() with no traversal check at all.

Restore is the more dangerous of the two — it overwrites live history from a directory you name.

FixFactor the validation into one _safe_backup_name() helper and call it from all three endpoints. This is also the fix that should be ported to NRL, where the delete path has no validation whatsoever.
SB-03Sin bin

Model artefacts are pickled

ml_model.py:390 pickles the bundle, :434 unpickles it. Same finding as NRL: unpickling executes arbitrary code, and the restore endpoint above is a path to writing that file. Here the bundle contains a DictVectorizer as well as the model, so the JSON alternative needs the vocabulary too — still entirely feasible, and it removes the scikit-learn version-pinning problem at the same time.

FixSerialise vocabulary, coefficients, intercept and metadata to JSON; reconstruct at load. Keep the feature_schema_version check you already have.

Section 03Architecture

SB-04Sin bin

Importing league_config renames files on disk

league_config.py ends with a bare call to _migrate_legacy_files() at module scope. Importing the module renames up to 19 state files, two log files, and relocates the entire espn_cache/ tree into a league subdirectory.

Three consequences. First, any import triggers it — a test, an ad-hoc script, a REPL session, an IDE's import resolver. Second, it is not concurrency-safe: monitor.py and server.py both import it, and two processes starting together can interleave the os.rename calls and the directory walk. Third, LEAGUE is read from the config file at import time and frozen, so a single process cannot handle two leagues — which is why operation requires NBA_MONITOR_CONFIG=… per process.

FixMake migration an explicit command (python3 -m tools.migrate) guarded by a lock file, and make league resolution a function call — get_league(config) — rather than import-time module state. That second change is also the prerequisite for the shared-package work in Section 06.

The two NameError defects are not coincidental to this. A 2,786-line function accumulates local state that helper functions elsewhere in the file want to read, and the only thing preventing them is that Python raises at runtime rather than at import. Extracting a CycleContext object — one dataclass holding config, state, now, season, sl_game_ids, passed explicitly to each helper — would make this class of bug structurally impossible rather than merely lintable.

Repository hygiene

  • 24 markdown files, 924 KB, at the repository root — SPEC-*, CHECKLIST-*, ISSUE-*, README_*, PROPOSAL-*, MODULE-OVERVIEW-*, plus a 433 KB CHANGES.md and a 57 KB README.md. Move the specs and checklists to docs/, archive completed ones, and split CHANGES.md by season.
  • dashboard.html is 1.09 MB and committed, with 270 inline onclick handlers and 8 aria- attributes across the whole file.
  • Dependencies are unpinned — requirements.txt is three lines of >=. Since model artefacts are pickled, a scikit-learn minor release can silently break load_for_inference(). Pin exact versions and keep a lock file.
  • No package structure — 51 modules flat at the root, with imports inside functions to dodge cycles.

Section 04Reliability & testing

SB-05Sin bin

Fifteen test files, and CI runs none of them

.github/workflows/ contains claude.yml and claude-code-review.yml. Both invoke the Claude Code action on pull requests. There is no job that runs pytest, no job that runs a linter, and no job that runs parity_check.py.

So the fifteen test_*.py files only execute when someone remembers to run them by hand, and the two NameErrors in Section 01 sailed through a review workflow that was, ironically, configured to catch exactly this.

FixAdd a workflow that runs ruff check . and pytest -q on every push. Ruff finds both send-off defects in under a second. Then add parity_check.py as a scheduled job against a fixed sample of games — you already built the hardest part.

Worth saying plainly: parity_check.py is very good

Replaying live-monitored games through the backfill path and asserting that conditions_fired matches is the correct answer to "is my historical data the same shape as my live data", and it is the check most projects of this kind never write. It supports an alternate baseline history file, config-fingerprint gating, cache-first replay and count-level assertions. It should be in CI, it should gate releases, and it should be the first thing ported to NRL — which has no equivalent at all.

Exception handling, again

Same pattern as NRL and for the same reason — both defects in Section 01 were converted into silence by broad handlers. The rule worth adopting across both repositories: catch specific exception types; where a broad catch guards a task boundary, use logging.exception() so the traceback reaches the log, and increment a counter the dashboard displays. A NameError should never be indistinguishable from "the API returned nothing".

Section 05Prediction & ROI analytics

This is where NBAMonitor is clearly ahead of the NRL fork — and where the remaining gap is a matter of connecting things that already exist rather than building them.

What is right here

build_training_rows() uses score_margin_at_fire and quarter_elapsed_pct — the state at the moment the condition fired — not the final scoreline. The NRL model uses the final margin as a feature against a "did they win" label, which is why it reports 98.9% accuracy and means nothing. This model does not have that flaw. It also carries pregame features, a FEATURE_SCHEMA_VERSION that is checked at inference, and class_weight="balanced". analyse_bk_odds.py computes Brier scores for synthetic against bookmaker probabilities and is candid in its own output about where vig calibration is not possible.

SO-05Send-off

The production model is fitted with no validation of any kind

_fit_variant() (ml_model.py:277) vectorises every row, fits a LogisticRegression, and returns sample_size and positive_rate. There is no cross_val_score, no train_test_split, no holdout, no calibration measurement — I searched the whole tree and the only appearances of those APIs are in evaluate_model.py, which evaluates the frequency and Bayesian models instead.

So you have a walk-forward harness (rolling_origin_predictions), a holdout function, brier(), log_loss() and calibration(bins=10) already written and already wired into the dashboard — and the model that actually produces predicted-winner calls never passes through any of it. Its reported quality is a sample count.

FixPoint the existing harness at ml_model. Add a fit_fn adapter so rolling_origin_predictions can drive it exactly as it drives fit_frequency and fit_bayesian, then publish Brier, log loss and the calibration table for all three side by side, with the de-vigged bookmaker probability as a fourth column. That comparison is the single most decision-useful thing the dashboard could show, and most of the code for it exists.
SB-06Sin bin

Rows are correlated within games, so naive CV will mislead

build_training_rows() emits one row per condition fire, so a single game can contribute a dozen highly correlated rows sharing the same label and the same pregame features. When you add cross-validation per SO-05, an ungrouped KFold will place rows from the same game on both sides of the split and report an inflated score — the same structural error the NRL model makes with its mirrored home/away rows.

FixStratifiedGroupKFold grouped on game_id, and prefer the rolling-origin split by date for anything you intend to bet on.
SB-07Sin bin

Deduplication keeps the first fire and discards the rest

dedupe_key = (game_id, condition_name, team_marker) — a condition that fires five times across a game contributes one row, and which one depends on the order of conditions_fired. That discards information (repeat firing is itself a signal) and makes the training set sensitive to list ordering, which is a property of how records were written rather than of the game.

FixEither keep every fire and group by game for validation, or make the choice explicit and principled — first fire, last fire, or an aggregate count feature — rather than a side effect of iteration order.
SB-08Sin bin

The −110 flat-juice assumption is inherited by both repositories

outcomes.py:402 defines FLAT_WIN_PROFIT = 100 × (100 / abs(FLAT_JUICE_ML)) ≈ 90.91, used whenever a real price is absent. It is at least documented and tested here (test_issue143_roi.py), which is better than the bare 90.91 literal in the NRL server — but it is the same substitution, and it means any ROI series mixing real and assumed prices is measuring two different things.

It is also an American convention. For an Australian book, −110 corresponds to decimal 1.909; typical NBA sides sit near 1.91 so it is close, but it should be an explicit configured assumption rather than a constant named after a US price format.

FixTag every stored price with provenance (real / synthetic / assumed), report ROI separately by provenance, and exclude assumed-price bets from any figure used for a decision.
SB-09Sin bin

The combo leaderboard carries the same multiple-comparisons exposure

audit_roi.py shares 72% of its function names with the NRL version, including the combo enumeration. The same critique applies: hundreds of role × margin × selection × period cells ranked by ROI, with no holdout, no minimum sample, no confidence interval and no correction for the number of hypotheses tested. NBA's larger history helps but does not solve it — more games also means more cells.

FixAs per the NRL review: minimum sample size, Wilson or bootstrap intervals displayed next to every ROI, discovery/validation season split, and Benjamini–Hochberg across the grid. Because audit_roi is 72% shared, this is one fix that lands in both projects if the module is shared — see Section 06.

Still missing in both

Neither project tracks closing-line value, keeps a bet ledger, models a bankroll, or sizes stakes by anything other than a flat 100. Those recommendations from the NRL review apply here unchanged, and they apply more urgently, because NBA has the larger history and the better-specified model — it is the codebase most likely to produce a strategy worth actually staking, and therefore the one that most needs an honest ledger behind it.

SO-06Send-off

The projects are already coupled — through hardcoded filesystem paths

NRLMonitor/pw_roi_report.py:21 contains:

NBA_DIR = os.path.join(os.path.expanduser("~"), ".openclaw/workspace/scripts/nba-monitor")
LEAGUES = {"NBA":  os.path.join(NBA_DIR, "game_history_nba.json"),
           "WNBA": os.path.join(NBA_DIR, "game_history_wnba.json"), …}

…and a --copy-to-nba flag that writes the generated report back into the other repository. So a cross-league ROI report already exists, and the integration mechanism is one repository reaching into another repository's working directory by absolute path.

That breaks on any machine laid out differently, silently produces a report with a missing league if the path is wrong, and means the schema of game_history_nba.json is now an undeclared public interface that NBAMonitor can break without knowing.

FixShort term, make the path configurable and validate it, failing loudly rather than silently omitting a league. Properly: define the history record as an explicit versioned schema owned by shared code, and have both projects read and write through it.

The recommended shape

The measured overlap suggests the split almost exactly. Extract a shared package, keep two thin sport adapters:

sportmonitor/                    # installable package, versioned, tested once
  core/       config, store (sqlite), cyclecontext, logging, secrets
  odds/       odds_api client, devig, synthetic pricing, price provenance
  analysis/   outcomes, roi (with CIs + multiple-testing correction),
              pw_trend, calibration, evaluate (walk-forward/Brier/log-loss)
  backup/     runtime_backup, restore, wal, safe_backup_name()
  web/        app skeleton, auth middleware, shared endpoints, static handler
  ml/         training harness, feature schema versioning, model registry
  parity/     live-vs-replay harness

adapters/
  nba/        espn client, basketball conditions, quarter semantics, team map
  nrl/        nrl.com client, league conditions, half semantics, team map

The adapter interface is small — fetch fixtures, fetch a game, normalise to a common record, evaluate sport conditions, describe period structure. Everything above 70% on the chart moves into sportmonitor; everything below 20% stays in an adapter. The monitor and server become thin: a scheduler and a router that hold a CycleContext and call into shared code.

Two consequences worth naming. First, league_config.py's VALID_LEAGUES = ("nba", "wnba") becomes an adapter registry, and NRL becomes the third entry rather than a fork — which is what it should have been. Second, the SQLite migration recommended for NRL should be designed once, in core/store, for both.

Migration without a big-bang rewrite

  1. Freeze the divergence. Before extracting anything, port the seven fixes in the table above so both repositories are at the same security and correctness baseline. This is a day of work and it is worth doing regardless of whether you proceed further.
  2. Extract the easy 90%. runtime_backup, pw_trend, synthetic_odds and the Odds API client are near-identical. Publish them as sportmonitor installed from a Git URL, and have both repositories import instead of vendor. Low risk, immediate payoff, and it establishes the pattern.
  3. Unify the record schema. Define the game history record explicitly with versioning. This is the prerequisite for sharing outcomes, audit_roi and the evaluation harness, and it retires the hardcoded path in pw_roi_report.py.
  4. Share the analysis layer. outcomes, audit_roi, evaluate_model, calibration and the ROI statistics move across. This is where the multiple-comparisons and confidence-interval work should land, so it is fixed once for every sport.
  5. Extract the web skeleton with auth built in. One authenticating server, two sets of sport-specific endpoints. This is also the natural moment to leave BaseHTTPRequestHandler.
  6. Adapters last. conditions and ml_model stay per-sport; only the training and evaluation harness is shared.

A reasonable stopping point is step 3. Steps 1–3 remove the security asymmetry, end the duplicated maintenance on the infrastructure modules, and give you a real data contract — which is most of the benefit for a fraction of the disruption. Steps 4–6 are worth doing if you expect to add a fourth league or if the analysis layer keeps growing, which on current evidence it will.

One argument against sharing, taken seriously

Forking let the NRL project move fast without risking a working NBA system, and that was a defensible trade at the time. A shared package means a change to outcomes can break both monitors at once, and that risk is real.

It is answerable, though, and cheaply: version the shared package and let each repository pin it, so upgrades are deliberate rather than automatic. Combined with the CI that both projects currently lack, that gives you most of the isolation of a fork with none of the divergence. The current arrangement has the opposite properties — full isolation of fixes, zero isolation of the data format they already share by absolute path.

Section 07Further recommendations

Specific to NBA/WNBA

  • Rest, travel and schedule load. The _check_b2b machinery in SB-01 shows back-to-backs are already understood as important. Extend it: days of rest for each side, third-game-in-four-nights, time-zone change, and altitude for Denver and Utah. These are among the best-documented effects in basketball betting and the market prices them imperfectly on the second night.
  • Rest-of-season and load management. Star availability is the dominant NBA variable and the one where an alert on late injury-report changes has clear practical value. WNBA has smaller rosters, so a single absence moves the line further.
  • Separate WNBA models. league_config already gives WNBA its own state files, and period length differs (10-minute quarters versus 12). Pace, variance and home advantage all differ enough that a shared model is a compromise; train and calibrate per league and compare.
  • Quarter-level live modelling. NBA has far higher scoring frequency than NRL, which means live win probability is more estimable and more of the value sits in-play. The quarter_elapsed_pct feature is already there — pair it with a time-decayed margin term.
  • Summer League as a separate regime. Training already excludes it. Worth confirming the same exclusion runs through the ROI analysis, since pricing and roster stability are entirely different.

Applying across both

  • De-vig everything before comparing model to market, and store both raw and fair probabilities.
  • Replace the confidence threshold with expected value, computed against the de-vigged price with an allowance for estimation error.
  • Closing-line value as the headline KPI, above ROI — it produces a usable signal in dozens of bets rather than hundreds.
  • A bet ledger and a paper-trading mode, with a pre-committed number of paper bets before any strategy is allowed to alert.
  • Fractional Kelly with a drawdown circuit-breaker, gated on the calibration work in SO-05.
  • Multi-book capture for best price and a better fair-price consensus.
  • Model registry and drift monitoring — rolling log loss by week, per league, per model variant.
  • Execution assumptions in the backtest — latency, slippage, and exclusion of signals firing during market suspension.

The same honest note as the NRL review

Nearly all of this improves measurement rather than return, and better measurement will often show that an apparent edge was not there. That is the point of it. NBA markets are among the most efficient and most heavily modelled in the world, the structural margin is real, and Australian bookmakers restrict accounts that win. An edge that survives everything above can still be difficult to realise at meaningful stakes.

Treat CLV as the honest scoreboard, size conservatively, decide the bankroll in advance, and keep the engineering interesting on its own terms — which, on the evidence of parity_check.py, it clearly is.
